# ADR-0001: ブランチ戦略とバージョニング

- Status: Accepted
- Date: 2026-11-08

## Context

- 開発者は1人。目的は設計・テスト設計・CI/CDの型の習得であり、CI/CDの練習機会を増やしたい。
- 計画(スコープ・フェーズ)は開発中に逐次変わる可能性がある。
- 成果物は静的ビューア(GitHub Pages)のみで、常駐サーバーやリリース系統の並行保守はない。

## Decision

### ブランチ戦略: GitHub flow

- `main` は常に緑(lint・型・テストが通る)で、公開物(Pages)の元になる。
- 変更は短命ブランチから Pull Request 経由で `main` に入れる(ソロでもPRを使う)。
- ブランチ名: `feat/…` `fix/…` `docs/…` `ci/…` `adr/…`。タスク単位で小さく切る。
- マージ方式: **通常のマージコミット**(squash・rebaseは使わない)。
  PR内のコミットは履歴に残るため、コミットメッセージは意味のある単位で書く。
- ブランチ保護(CI必須・`main`直push禁止)は、最初のCIが動いて
  必須チェック名が確定した後に GitHub の Settings で設定する。

### バージョニング: SemVer (`v0.MINOR.PATCH`)

- 1.0 未満の間は破壊的変更を許容する。
- タグは `main` のマージコミットに打つ。
- 目安(フェーズ完了時にMINORを上げる):

| タグ | 内容 |
|---|---|
| `v0.0.1` | Phase 0 完了(雛形・CI・Pages) |
| `v0.1.0` | Phase 1 完了(最小MVP) |
| `v0.2.0` | Phase 2 完了(比較の第一歩) |
| `v0.3.0` | Phase 3 完了(ソルバ拡充) |
| `v0.4.0` | Phase 4 完了(動的。分散は ADR-0010 で外した) |

- フェーズ内の区切りや修正は PATCH を上げる。この対応表は目安であり、計画変更時は更新する。

## Consequences

- (+) `main` が常に動く状態なので、計画変更に追従しやすい。
- (+) PR → CI → マージ → Pages の流れ自体が学習対象になる。
- (+) タグが成果物の状態を表し、計画(フェーズ)の変更から独立する。
- (−) マージコミットにより履歴が squash より冗長になる。
- (−) ブランチ保護は手動設定で、コードとして管理されない(必要なら後でADR化)。

## Alternatives considered

- **Git Flow**: `develop`/`release` ブランチはソロ・単一系統では管理コストが勝つ。
- **mainへの直push(trunk-based)**: CI/PRの練習機会が減る。
- **フェーズ名でのタグ(`phase-0` 等)**: 計画変更でタグの意味が崩れるため不採用。
- **squash マージ**: 履歴は簡潔になるが、現時点で運用経験がないため通常マージを採用。
  必要になれば本ADRを更新する。
