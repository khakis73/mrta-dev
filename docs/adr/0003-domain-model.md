# ADR-0003: ドメインモデルと問題定義

- Status: Accepted
- Date: 2026-11-09

## Context

- 全ソルバを同じ問題で比較するため、**問題の定義と指標の計算方法を最初に固定する**必要がある。
  後から変えると、ソルバ・シミュレータ・ビューア・ログの全てに波及する。
- 目的は設計・テスト設計・CI/CDの習得であり、題材の作り込みは目的外(CLAUDE.md)。
  現実のロボット運用を再現するのではなく、**ソルバの違いが見える最小の問題**にする。
- 後のフェーズで次を使う。モデルはこれらに拡張できる形にしておく。
  - Phase 2: ハンガリアン法(割当問題)
  - Phase 3: CP-SAT(**整数**しか扱えない)、Routing、下界
  - Phase 4: 動的なタスク到着
- スコープ外: 経路の衝突回避、ロボットの物理挙動(README)。

## Decision

### 問題の種類

**静的なマルチロボット・タスク割当(MRTA)** とする。全タスクは時刻0で既知。
(Phase 4 で、タスクの到着時刻 `release_time` を足して動的に拡張した。静的は全タスクが 0 の場合。ADR-0011)
各タスクは**ちょうど1台**のロボットに割り当て、ロボットごとに実行順を決める。

### 空間と時間は整数で表す

- 空間: 矩形の**整数格子**。障害物はなく、衝突も考えない。
- 距離: **マンハッタン距離**。
- 時間: **整数ティック**。速度は「1ティックに進める格子数」(正の整数)で、
  移動時間は `ceil(距離 / 速度)`。
- 理由: CP-SAT が整数しか扱えず、**下界を厳密に計算できる**ため。丸めの規約を各ソルバに持たせない。
  浮動小数点の比較・誤差を避けられ、決定性(テスト、ログの比較)も守りやすい。

### エンティティ

| エンティティ | 属性 |
|---|---|
| `Robot` | `id`、`kind`、`start`(初期位置)、`speed`、`capacity`、`skills`(スキルの集合) |
| `Task` | `id`、`location`、`required_skill`、`demand`、`service_time` |
| `Scenario` | `seed`、格子の大きさ、`robots`、`tasks` |
| `Plan`(ソルバの出力) | ロボットID → **実行順に並んだタスクIDのリスト** |

- ID は `r0, r1, …` / `t0, t1, …` の決定的な文字列。
- `Plan` は**全ロボットのIDをキーに持つ**(タスクが0件のロボットは空リスト)。
  キーの欠落・余分なキーは不正な `Plan` とする。
- `kind` は `amr` と `mobile_manipulator`。種別は**属性の組み合わせ**で表し、
  ソルバは `kind` を見ず、スキルと容量だけを見る(下記)。
- 異種性は次で表現する。

| | AMR | モバイルマニピュレーター |
|---|---|---|
| 速度 | 速い | 遅い |
| 容量 | 大きい | 小さい |
| スキル | 運搬(`carry`) | 運搬と操作(`carry`、`manipulate`) |

### 制約

1. **割当の完全性:** 全タスクがちょうど1回、いずれかのロボットに割り当てられる。
2. **スキル制約:** `task.required_skill ∈ robot.skills`。
3. **容量制約:** `task.demand <= robot.capacity`(**タスクごとの可否**であり、累積しない)。
   累積容量(複数タスクの積載)は、本格的なルーティング問題になるためMVPでは扱わない。

シナリオ生成器は、**全タスクに適格なロボットが1台以上いる**シナリオだけを出力する。
適格なロボットがいないタスクがあれば、ソルバは明示的に例外を投げる(黙って捨てない)。

### 実行の意味(シミュレーション)

- ロボットは `start` から出発し、`Plan` の順にタスクを実行する。
  各タスクは「移動 → `service_time` ティックの作業」。**最後のタスクの後は帰還しない**(開いた経路)。
- ロボット同士は干渉しない(衝突なし)。ロボットの完了時刻は、自分の経路だけで決まる。
  静的(全タスクの `release_time` が 0)では待ち時間もない。動的では、到着前のタスクへは出発せず、
  出発前に待つ(ADR-0011)。ロボットの `ready_at`(既定 0)までは出発できない(ADR-0012)。
- タスクが0件のロボットの完了時刻は0。

### 指標(計算式を固定する)

| 指標 | 定義 |
|---|---|
| 完了時間(makespan) | 全ロボットの完了時刻の最大値 |
| 総移動距離 | 全ロボットの移動距離(マンハッタン)の総和 |
| 稼働率 | `全ロボットの稼働時間(移動+作業)の総和 / (ロボット数 × 完了時間)` |
| 下界ギャップ | `(完了時間 − 下界) / 下界`。**下界の定義と計算はPhase 3で別ADRにする** |

- 稼働時間の移動は、`ceil` 後のティック数で数える。
- 完了時間が0のとき、稼働率は定義しない(`None`)。
- Phase 1・2では下界ギャップを出さない。

### コード上の置き方

- Python の不変なデータクラス(`@dataclass(frozen=True, slots=True)`)。検証は `__post_init__`。
- `mrta.model`(エンティティ)、`mrta.scenario`(生成器)、`mrta.solvers`、`mrta.sim`
  (実行と指標)に分ける。**ソルバは `Scenario → Plan` の純関数**とし、シミュレータを知らない。
- 乱数は `random.Random(seed)` を明示的に渡す(グローバルを使わない)。
  同点の解消は、IDの辞書順など**決定的な規則**で行う。
- JSONLのスキーマは別のADR(ADR-0004)で決める。

## Consequences

- (+) 全ソルバが同じ入出力(`Scenario → Plan`)を持つため、共通の契約テストが書ける。
  - 全タスクがちょうど1回割当、スキル・容量制約を満たす、など。
- (+) 整数だけで閉じるので、CP-SAT の最適解と下界を厳密に比較できる。
- (+) 指標の定義がADRで固定され、ソルバ間・フェーズ間で比較できる。
- (−) **現実のモデルから大きく単純化している。**
  - 干渉がない、累積容量がない、帰還しない、マンハッタン距離。
  - 結論を現実に一般化してはいけない。ADRとREADMEにこの前提を明記する。
- (−) **干渉がないため、割当の優劣は主に負荷の偏りと移動の効率で決まる。**
  ソルバ間の差が小さい場合は、題材(シナリオ)側を調整する。
- (−) `ceil` による丸めで、速度差が小さい場合に移動時間の差が潰れることがある。
  シナリオの格子を十分大きくして緩和する。

## Alternatives considered

- **連続空間 + ユークリッド距離 + 浮動小数点:** 直感的だが、CP-SAT に渡すには丸めが必要で、
  下界の厳密性と決定性が弱くなる。
- **ピックアップ・デリバリーのペアと累積容量:** 現実に近いが、問題が VRP になる。
  MVPの目的(ソルバの違いの理解)に対して重く、割当とルーティングの切り分けが難しくなる。
- **帰還あり(デポに戻る):** 経路のコストが対称になるが、完了時間の意味が「全員が戻る時刻」になり、
  タスクの価値と無関係な帰路の移動が入る。開いた経路のほうが単純。
- **ロボットの種別ごとにクラスを分ける:** 型は明確だが、ソルバが種別で分岐しやすくなる。
  属性(スキル・容量・速度)で表し、ソルバをスキルと容量だけに依存させる。
- **pydantic を使う:** 検証とJSON変換が楽だが、依存が増える。MVPでは標準のデータクラスで足り、
  JSONLの変換はスキーマ(ADR-0004)で扱う。

## 見直しの条件

- ソルバ間の差が出ず、比較の意味が薄いことがシナリオ調整でも解消できない。
- 累積容量・帰還・動的到着が必要になる(Phase 3・4)。拡張時は本ADRを更新するか、新しいADRで上書きする。
