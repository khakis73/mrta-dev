# ADR-0004: JSONLログのスキーマ

- Status: Accepted
- Date: 2026-11-09

## Context

- Pythonコア(書く側)と TypeScript ビューア(読む側)は、**ログだけでつながる**。
  両者は別言語・別ビルドで、ログの形がそのまま2つのコンポーネントの契約になる。
- ビューアは静的ホスティング(GitHub Pages)で動き、ブラウザ内で完結する。サーバーはない。
- 後続フェーズでの使われ方:
  - Phase 1: 1つのログを1画面でリプレイする。
  - Phase 2: **同じシナリオ**に対する2つのログを、2画面で同期して比較する。
  - Phase 3: ベンチマーク(複数シード)と下界。
  - Phase 4: 動的なタスク到着(実行中にイベントが増える)。
- ADR-0003 により、位置・時間・距離は全て整数。決定性(同じ入力 → 同じ出力)を守る(CLAUDE.md)。
- 学習目的なので、**言語間の契約を壊れにくくする仕組み**(スキーマ、共有テストデータ)の型も身につけたい。

## Decision

### 形式: 1実行 = 1ファイル(JSONL)

- 1行 = 1つのJSONオブジェクト。文字コードは UTF-8、改行は LF、**ファイル末尾も改行**で終える。
- **ログは決定的にする。** 同じシナリオ・同じソルバ設定なら、**バイト列が完全に一致**する。
  - 数値は全て**整数**(浮動小数点を出力しない)。
  - 各行は**キーをソート**し、区切りは `,` と `:`(空白なし)、非ASCII文字はエスケープして出力する。
    Python では `json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=True)` に固定する。
  - **IDの並びは、文字列としての辞書順**とする(`r0, r1, r10, r2` の順。数値順ではない)。
    キーのソートと同じ規則になり、言語間で一致する。
  - 行の順序は下記の規則で固定する。
- **壁時計の時間(実行時間)は書かない。** 実行のたびに変わり、決定性を壊すため。
  必要になったら(Phase 3 のベンチマーク)、ログとは別のファイルに分ける。
- パッケージのバージョンも書かない(リリースのたびに、テスト用の固定ファイルが変わるため)。

### 行の種類と順序

`type` で行の種類を判別する。順序は次のとおりで、`header` が先頭、`metrics` が末尾。

| 順 | `type` | 個数 | 内容 |
|---|---|---|---|
| 1 | `header` | 1 | `schema_version`(整数) |
| 2 | `scenario` | 1 | シナリオ全体(ビューアが再構成できる) |
| 3 | `solver` | 1 | ソルバ名と、結果に影響する設定 |
| 4 | `plan` | 1 | ソルバの出力(ADR-0003 の `Plan`) |
| 5 | `segment` | 0個以上 | 実行の記録。ロボットの時間区間 |
| 6 | `metrics` | 1 | 指標。**末尾の行は、ファイルが完結している印**でもある |

- 末尾が `metrics` でないファイルは、**途中で切れたもの**として、読む側が拒否する。
- Phase 4 で、実行中のイベントが増える場合は、`segment` の後ろに行の種類を足せる(追記しやすい形)。

### 各行のフィールド

位置は `[x, y]`(整数2要素)、IDは文字列(ADR-0003)。

```jsonl
{"schema_version":1,"type":"header"}
{"height":10,"robots":[{"capacity":5,"id":"r0","kind":"amr","skills":["carry"],"speed":2,"start":[0,0]}],"seed":42,"tasks":[{"demand":1,"id":"t0","location":[3,4],"required_skill":"carry","service_time":2}],"type":"scenario","width":10}
{"config":{},"name":"greedy","type":"solver"}
{"routes":{"r0":["t0"]},"type":"plan"}
{"from":[0,0],"kind":"move","robot":"r0","t0":0,"t1":4,"task":"t0","to":[3,4],"type":"segment"}
{"from":[3,4],"kind":"service","robot":"r0","t0":4,"t1":6,"task":"t0","to":[3,4],"type":"segment"}
{"available_total":6,"busy_total":6,"makespan":6,"per_robot":{"r0":{"busy":6,"distance":7,"finish":6}},"total_distance":7,"type":"metrics"}
```

(上は説明用に短くした例。キーは実際の出力と同じくソート済み。)

- **`scenario`**: `seed`、`width`、`height`、`robots`(`id`、`kind`、`start`、`speed`、`capacity`、
  `skills`)、`tasks`(`id`、`location`、`required_skill`、`demand`、`service_time`)。
  `robots` と `tasks` は **IDの辞書順**、`skills` は**辞書順**に並べる。
- **`solver`**: `name` と `config`(結果を左右する設定。例: `num_workers`、時間制限)。
  再現に必要な設定は、ここに残す。
  - `config` の値も**整数・文字列・真偽値**に限る。時間は整数のミリ秒で書く(例: `time_limit_ms`)。
- **`plan`**: `routes`。**全ロボットのIDをキーに持ち**、値は実行順のタスクID(ADR-0003)。
- **`segment`**: ロボットの**時間区間**。
  - `kind` は `move`(移動)と `service`(作業)。`service` では `from` と `to` が同じ位置。
  - `t0 <= t1`(ティック)。**長さ0の区間は出力しない**。
  - 並びは `t0`、ロボットID、`kind`(`move` が先)の順。
  - 移動は、**x方向に進んでから y方向に進む**ものとして描く(マンハッタン距離)。
    ビューアが区間内の位置を線形補間して描くのは**表示のためだけ**で、
    実行の意味を再計算してはならない(ビューアは時刻と位置を、ログから読むだけにする)。
- **`metrics`**: `makespan`、`total_distance`、`busy_total`(稼働時間の総和)、
  `available_total`(ロボット数 × `makespan`)、`per_robot`(ロボットIDごとの `finish`、
  `distance`、`busy`)。
  - **稼働率は、割り算した値を書かない。** 整数の分子と分母(`busy_total`、`available_total`)を書き、
    比はビューアが計算する(浮動小数点を避けるため)。`available_total` が0なら、稼働率は未定義として「—」と表示する。
  - 下界ギャップは Phase 3 の別ADRで追加する(後方互換な追加。下記)。

### スキーマ検証と共有テストデータ

- **JSON Schema** を、契約の正とする。`schema/log-v1.schema.json`(1行の検証用、`type` で分岐)。
  行の個数・順序のような**ファイル全体の規則**は、スキーマでは書けないため、
  Python側の検証関数と、そのテストで保証する。
- Python側: ログの書き出しを、スキーマ(`jsonschema`)で検証するテストを置く。
- **共有のテストデータ(golden file)**:
  `tests/golden/*.jsonl` に、固定シードで生成したログをコミットする。
  - Pythonのテスト: 生成したログが golden と**バイト一致**する(決定性の検証)。
  - ビューアのテスト: **同じファイル**を読み込み、パースと表示ができる(読み側の契約テスト)。
  - 仕様を変えたら golden を更新する。その差分がレビュー対象になる。
- TypeScriptの型は**手書き**し、必要な項目だけ実行時に検証する。
  スキーマからの自動生成は、規模が増えてから検討する(新しい道具を増やさない)。

### バージョニングと互換性

- `schema_version` は**整数**で、互換性を壊す変更のときだけ上げる。
- **後方互換な変更**(任意のフィールドの追加、行の種類の追加)は、バージョンを上げない。
  読む側は、**未知のフィールドと未知の `type` の行を無視する**。
  - 追加する行は、`header` の後から `metrics` の前までに置く。`metrics` は常に末尾で、
    その後ろに行があるファイルは不正とする。
- **互換性を壊す変更**(フィールドの削除・意味の変更・必須化)は、バージョンを上げる。
  ビューアは、対応しない版を**明示的なエラー**で拒否する(黙って誤表示しない)。
  ファイルは `schema/log-v2.schema.json` のように、版ごとに分けて残す。

### 配置と配信(概要)

- 公開用のログは、**Pages のビルド時に Python で生成**する(リポジトリにコミットしない)。
  コードとログが常に一致する。
- ビューアは、**URLのクエリ**(例: `?log=data/xxx.jsonl`)で読み込むログを指定する。
  Phase 2 では、同じシナリオの2つのログを指定し、**`scenario` 行が一致すること**を
  比較の前提として確認する(決定的な出力なので、行の比較で足りる)。
- ログの一覧(マニフェスト)は、必要になった時点(Phase 2 以降)で別に決める。

## Consequences

- (+) **ビューアに実行のロジックを複製しない。** 実行の意味(移動時間の `ceil`、待ち)は
  Pythonだけが持ち、ログが事実を運ぶ。2言語で食い違うリスクを避けられる。
- (+) バイト一致のgolden fileが、**決定性**と**言語間の契約**を一度に守る。
- (+) 整数だけなので、`JSON.parse` での数値の誤差や、言語間の丸めの差が出ない。
- (+) 2つのログの `scenario` 行を比べるだけで、2画面比較の前提(同じ問題か)を確認できる。
- (−) **`segment` が冗長**。`plan` とシナリオから導出できる情報を、ログに書いている。
  1ログあたり数十〜数百行で、規模としては問題ないが、巨大なシナリオには向かない。
- (−) **スキーマ(JSON Schema)と、Pythonのモデルと、TypeScriptの型の3か所に同じ形がある。**
  手書きの重複で、golden file とテストで乖離を検出する形にしている。変更のたびに3か所を直す。
- (−) ファイル全体の規則(個数・順序)はスキーマで書けず、検証が分散する。
- (−) 実行時間をログに書かないため、ベンチマークで時間を見るなら、別の仕組みが要る。
- (−) **壁時計の時間制限を持つソルバ(Phase 3 の CP-SAT)は、バイト一致を保証できない。**
  `num_workers=1` でも、時間制限内に進む探索の量はマシンの速さで変わり、解が変わりうる。
  golden file に載せるソルバは、決定的な停止条件(CP-SAT の `max_deterministic_time` など)で
  止まるものに限る。具体的な設定は Phase 3 の ADR で決める。

## Alternatives considered

- **1つのJSONファイル(JSONLにしない):** Phase 1 では十分で、読み書きも単純。
  JSONLを選ぶのは、行ごとの差分が読みやすいことと、Phase 4 で行を追記できることのため。
  Phase 1 の範囲だけなら、単一JSONのほうが単純であることは認める。
- **ビューアが `scenario` と `plan` から位置を再計算する(`segment` なし):**
  ログは小さくなるが、移動時間の丸めなどの意味を TypeScript に複製することになり、
  2言語の食い違いが起きる。ログに事実を書くほうを選ぶ。
- **ティックごとの全ロボット位置(フレーム列):** ビューアは単純だが、ログが大きく冗長。
  時間区間のほうが小さく、補間も単純。
- **浮動小数点で時刻・距離を書く:** ADR-0003 の整数方針と矛盾し、決定性とバイト一致が脆くなる。
- **Python(pydantic)のモデルからスキーマを生成し、TypeScriptの型も生成する:**
  重複は減るが、依存と生成の手順が増える。MVPでは手書きの契約テストで足りる。
- **バイナリ形式(MessagePack・Protocol Buffers・Parquet):** 人が読めず、差分も取れない。
  この規模では、サイズの利点より、可読性とレビューのしやすさを優先する。

## 見直しの条件

- ログが大きくなり、ファイルサイズや読み込み時間が問題になる(圧縮、`segment` の間引き、形式の変更)。
- Phase 4 の動的イベントで、行の順序や種類の規則が成り立たなくなる。
- 決定的な停止条件で止めたソルバでも、golden file のバイト一致が保てない(環境・ライブラリ版の差)。
- 手書きの3か所の同期が負担になり、乖離が頻発する(スキーマからの型生成を導入する)。
