# ADR-0005: ハンガリアン法ソルバと手作りシナリオ

- Status: Accepted
- Date: 2026-11-10

## Context

- Phase 2 の目的は「比較の第一歩」。貪欲法と、性質の異なるソルバ1つを**同じ問題**で比べ、
  違いが見える状態にする(README)。
- ハンガリアン法は**1対1の割当問題**(ロボット1台にタスク1つ)の最適解法である。
  一方、ADR-0003 の問題は**1台が複数タスクを順に実行する**ため、そのままは当てはまらない。
  「どう当てはめるか」が設計判断になる。
- 貪欲法は**タスクの処理順に依存**し、各ステップの局所最適しか見ない。
  その弱点が出るシナリオを手で作り、比較の根拠(再現できる例)にしたい。
- 制約: ソルバは `Scenario → Plan` の純関数、`kind` を見ない、ロボット順に依存しない、決定的
  (ADR-0003、契約テスト)。依存は増やさない(CLAUDE.md: 学習優先で小さく)。

## Decision

### ハンガリアン法の当てはめ: ラウンド方式

タスクが残る限り、次を繰り返す。

1. 各ロボット `r` と残りタスク `t` について、費用 `cost(r, t)` を
   「`t` を `r` の現在の経路の末尾に足したときの `r` の完了時刻」とする
   (`r` の現在の完了時刻 + 移動 `ceil` + 作業時間。貪欲法と同じ式)。
   `r` が `t` に不適格(スキル・容量)なら**割当不可**。
2. ロボット ↔ タスクの割当問題(各ロボットは高々1タスク、各タスクは高々1ロボット)を、
   **費用の総和が最小**になるように解く。割当可能なペアの数は**最大**にする。
3. 選ばれたペアを経路の末尾に確定し、ロボットの位置と完了時刻を更新する。

- ロボット数が残りタスク数以上なら全タスクが1ラウンドで決まり、そうでなければ複数ラウンドになる。
- 各ラウンドは、割当可能なペアが1つ以上ある(残りの各タスクには適格なロボットがいる)ので、
  必ず進む。

### 実装: 自前のハンガリアン法(O(n³)、整数のみ)

- 長方形(行 ≤ 列)の最小費用割当を、ポテンシャル法(Kuhn–Munkres)で実装する。
  ロボット数 > タスク数のときは転置する。
- **割当不可は大きな定数 `BIG`** で表す。`BIG` は「割当可能なペアだけでできる任意の割当の総和」
  より大きくする(`BIG = (行数) × (最大の有限費用 + 1) + 1`)。これで、最小費用の割当は
  割当不可のペアを最少にし、割当可能なペアが最大になる。選ばれた `BIG` のペアは捨てる。
- 整数だけで計算する(ADR-0003)。scipy は使わない(依存を増やさない。学習対象でもある)。
  テストで**全探索の最適解と一致**することを確認し、自前実装の正しさを担保する。

### 決定性

契約(ロボット順に非依存、再現可能)を守るため、**ロボットとタスクをIDの辞書順に並べてから**
行列を作る。同費用の最適解が複数あるとき、どれを選ぶかは行列の並びで決まるため、
並びを正規化する。`Scenario.tasks` の順序には依存しない(貪欲法との違い)。

### 手作りシナリオ

- `mrta.catalog` に、**名前つきの固定シナリオ**を置く(シードを持たない手書きの `Scenario`)。
  CLI は `--scenario NAME` で指定できる(`--seed` と排他)。
  ログの `scenario.seed` は 0 とする(手作りには意味を持たない)。
- `greedy-trap`: 2台・2タスクで、貪欲法が先に処理するタスクを近いロボットに
  割り当てた結果、もう一方のタスクの移動が長くなる(完了時間 貪欲法 11 / ハンガリアン法 6)。
  ハンガリアン法は2タスクを同時に見る。
- `skill-trap`: 運搬タスクを近いマニピュレーターが取り、そのマニピュレーターしかできない
  操作タスクが待たされる(貪欲法 5 / ハンガリアン法 3)。スキル制約が絡む失敗例。
- **この例が腐らないよう、テストで固定する**: 手作りシナリオごとに「どのソルバがどの指標でどれだけ
  良いか」をテストに書く(`greedy-trap` では、ハンガリアン法の完了時間が貪欲法より短い)。

### 2画面比較ビューア

別ADR(ADR-0006)で決める。本ADRはソルバとシナリオまでを範囲とする。

## Consequences

- (+) 既存の契約テスト(`SOLVERS` に登録するだけ)がそのまま効く。
- (+) タスクの処理順に依存しないので、貪欲法との差が「順序依存」として説明できる。
- (+) 手作りシナリオが、比較の再現できる根拠とテストの両方になる。
- (−) **ラウンドごとの総和最小は、全体の最適ではない。**
  - ラウンドの内側は最適だが、ラウンド間は貪欲(先のラウンドの確定が後を縛る)。
  - 目的が「完了時刻の総和」であり、評価指標の**完了時間(makespan)とは別物**。
    makespan では貪欲法に負けるシナリオ・シードがありうる。
    1シナリオの勝ち負けで結論しない(CLAUDE.md)。統計は Phase 3 のベンチマークで扱う。
  - **実装時の予備測定**(シード 0〜199 の生成シナリオ、完了時間。ベンチマークではない目安):

    | 設定 | ハンガリアン法の勝ち/負け/同点 | 平均完了時間 貪欲/ハンガリアン | 平均移動距離 貪欲/ハンガリアン |
    |---|---|---|---|
    | 既定(4台・10タスク) | 111 / 68 / 21 | 32.6 / 30.7 | 109.4 / 86.9 |
    | 4台・6タスク | 81 / 64 / 55 | 21.7 / 21.2 | 63.8 / 57.7 |
    | 4台・4タスク | 41 / 61 / 98 | 16.7 / 17.6 | 41.5 / 40.8 |

    タスクがロボット数に近いほど優位が薄れ、**4タスクでは平均の完了時間が貪欲法より悪い**。
    一方、移動距離はどの設定でも短い(総和最小化が効く)。
    つまり「ハンガリアン法のほうが良い」とは言えず、**完了時間と総移動距離でトレードオフがある**。
  - 全体の最適(下界との比較)は Phase 3(CP-SAT)で得る。
- (−) 自前実装は保守の対象。ただし小さく、全探索との一致テストで守る。
- (−) 手作りシナリオは**ソルバの弱点を狙って作った**例であり、典型的な性能の代表ではない。
  README と ADR に「見せるための例」と明記する。
- (−) `--scenario` で生成器を通らないシナリオが入る。`Scenario` の検証と、
  `unservable_tasks` の確認は引き続きソルバ側で行う(生成器の保証に頼らない)。

## Alternatives considered

- **scipy の `linear_sum_assignment`:** 速く確実だが、numpy/scipy の依存が増え、
  アルゴリズムを学ぶ機会がない。決定的な同点処理も制御しづらい。
- **ロボットの複製(1台を「第1のタスク枠、第2のタスク枠…」に展開)して1回で解く:**
  費用が前のタスクに依存するため、1回の割当問題に落とせない(経路依存)。
- **全体のタスクを1回で割り当てる(巡回順は別問題として切り離す):**
  割当とルーティングを分けるのは Phase 3 の Routing の話で、ここでは扱わない。
- **ボトルネック割当(最大費用の最小化):** makespan に近い目的だが、実装が増え、
  「ハンガリアン法」という題材から外れる。
- **ランダムなシナリオだけで比較する:** 弱点が出るとは限らず、違いが見えない可能性がある。
  手作りシナリオで原因が追える例を先に持つ。

## 見直しの条件

- 統計(複数シード)で、ハンガリアン法が貪欲法と有意に変わらない、または悪い場合
  (目的を makespan に寄せる、ボトルネック割当を検討する)。
- 手作りシナリオが増え、`mrta.catalog` の管理が負担になる(データファイル化を検討する)。
