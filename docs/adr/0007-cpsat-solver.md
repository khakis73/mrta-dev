# ADR-0007: CP-SAT ソルバ

- Status: Proposed
- Date: 2026-11-10

## Context

- Phase 3 の目的は「ソルバ拡充」と「下界ギャップ」(README)。これまでの貪欲法・ハンガリアン法は
  どちらも**ヒューリスティック**で、「最適解からどれだけ離れているか」が分からない。
  最適解(または証明つきの下界)を出せるソルバが、比較の物差しになる。
- ADR-0003 は、整数の問題として定義した理由に「CP-SAT が整数しか扱えず、下界を厳密に計算できる」ことを挙げた。
  本ADRはその前提を実装に落とす。
- 本ADRの範囲は **CP-SAT ソルバ(makespan 最小化)** まで。下界の定義とベンチマークは ADR-0008、
  Routing は ADR-0009 で別に決める(試作の知見は末尾)。
- 制約(ADR-0003、契約テスト): ソルバは `Scenario → Plan` の純関数、`kind` を見ない、
  ロボット順に依存しない、決定的。CLAUDE.md の方針: `num_workers=1`、制限は固定、整数のみ。
- **ここまで依存ゼロ**(`pyproject.toml` の `dependencies = []`)。初めて外部ライブラリを入れる。

## Decision

### 依存: OR-Tools を通常の依存に追加する

- `ortools` を `dependencies` に入れ、`uv.lock` で固定する(CI は `uv sync --locked`)。
- `mrta.solvers.cpsat` の先頭で import する。遅延 import や extras にはしない
  (`mrta publish` などからも使え、構成を単純に保つため。起動時間の増加は許容する)。

### 定式化: ロボットごとの circuit 制約

ロボット `r` と、`r` に適格なタスクの集合 `E_r` ごとに、ノード `{0(開始位置)} ∪ E_r` の
**開いた経路**を `AddCircuit` で表す。

- アーク `i → j`(`j ∈ E_r`)のリテラル `x[r,i,j]`。費用は
  `travel_ticks(manhattan(i, j), r.speed) + service_time(j)`(ADR-0003 の実行の意味と同じ)。
- タスクを訪問しない場合は自己ループ `j → j`。訪問リテラル `v[r,j]` はその否定。
- **開いた経路**(帰還しない): 「最後のタスク → ノード0」のアークを**費用0**で置く。
  何も訪問しないロボットは `0 → 0` の自己ループ(ノード0の自己ループは1本だけ。
  終端アークの `i=0` と兼ねる。試作で重複して `MODEL_INVALID` になった)。
- 各タスクはちょうど1台に割り当てる: `Σ_r v[r,t] = 1`。
- ロボットの完了時刻 `f_r = Σ(アーク費用)`。**待ちがない**(ADR-0003)ので、これで足りる。
  時刻の変数やタスク間の大M制約は要らない。
- スキル・容量は、適格なロボットだけに変数を作ることで表す(`is_eligible` を使う)。

### 目的: 2段階の辞書式最適化

1. **makespan を最小化**する(`max_r f_r`)。ここで得た値 `M*` と、探索が証明した下界を
   `CpSatResult` に残す(ADR-0008 の下界ギャップに使う)。
2. `max_r f_r ≤ M*`(段階1の解の値)を制約にして、**総移動距離**(マンハッタン距離の総和。
   指標と同じもの)を最小化する。

- 理由: makespan だけだと、律速でないロボットが無駄に動き回る最適解が返りうる。
  4つの指標のうち2つ(完了時間・総移動距離)を、定義どおりに順序づけて扱う。
- 重みつきの単一目的(`M×K + 距離`)にしない: 1回で解けるが、探索が返す下界が
  makespan と距離の混合になり、makespan の下界として使いにくい。
- 段階1が最適性を証明できなかった(`FEASIBLE`)場合も、段階2は得られた解の値を上限にして続ける。

### 決定性

- **入力の正規化:** ロボットとタスクを ID の辞書順に並べてからモデルを作る
  (`Scenario` の並びに依存しない。ハンガリアン法と同じ)。
- **設定を固定する:** `num_workers=1`、`random_seed=0`。
- **打ち切りは決定的時間で行う:** `max_deterministic_time`(CP-SAT が数える、マシン非依存の作業量)を使い、
  **壁時計の `max_time_in_seconds` は使わない**。
  壁時計だと、負荷によって打ち切り位置が変わり、解が変わりうる
  (予備測定: 壁時計1秒の打ち切りでは決定的時間が 1.28 / 1.29 とばらついた。
  同一マシンでは再現したが、境界上にあり保証できない)。
  決定的時間では同じ入力から同じ解が得られた。
- config は `{"num_workers": 1, "random_seed": 0, "det_time_limit_ms": …}`
  (ADR-0004: 整数。名前に `time` を含む設定は `_ms` で終える契約テストに合わせる。
  値は「決定的時間の秒 × 1000」で、壁時計のミリ秒ではない。docstring と本ADRに明記する)。
  段階ごとの上限とし、既定は 各5000(= 決定的時間5)。
- **フォールバック:** 段階1の探索に、貪欲法の `Plan` を**ヒント**(`AddHint`)として渡す。
  打ち切られても実行可能解が残る(貪欲法以上の解)。
- **限界(正直に書く):** 同じ OR-Tools のバージョン・ビルドでの再現を保証する。
  最適解が複数あるとき、**どの最適解が選ばれるか**は、OR-Tools の版や OS で変わりうる。
  したがってテストは `Plan` の一致ではなく、**makespan と総移動距離の値**を検証する
  (同一プロセス内の再現性だけ、契約テストで `Plan` の一致を見る)。

### インタフェース

```python
@dataclass(frozen=True, slots=True)
class CpSatResult:
    plan: Plan
    status: Literal["optimal", "feasible"]  # makespan について証明できたか
    makespan: int
    makespan_bound: int  # 証明された下界(optimal なら makespan と一致)

def solve_cpsat(scenario: Scenario, config: CpSatConfig = ...) -> CpSatResult: ...

class CpSatSolver:  # Solver プロトコル
    name = "cpsat"
    def solve(self, scenario) -> Plan:  # solve_cpsat(...).plan
```

- `Solver` プロトコル(`Scenario → Plan`)は変えない。ログの形式(ADR-0004)も変えない。
- `status` と下界は**ログには載せない**。ベンチマーク(ADR-0008)が `solve_cpsat` を直接呼んで使う。
- `SOLVERS["cpsat"]` に登録する。共通の契約テストと、ビューアの2画面比較(同じシナリオの2ログ)は
  そのまま使える。

### テスト

- **全探索との一致(正しさの根拠):** 小さなシナリオ(ロボット ≤ 3、タスク ≤ 5)で、全ての割当と順序を
  列挙した最適 makespan と一致する。同じ makespan の中で総移動距離も最小である。
- **オラクルとしての性質:** `optimal` のとき、他の全ソルバ(貪欲法・ハンガリアン法)の
  makespan が CP-SAT 以上である(property-based)。
- **契約テスト:** `SOLVERS` への登録で自動的に対象になる。ただし既存の戦略
  (最大30タスク・8台)は CP-SAT には重く、時間制限に到達して遅くなる。
  契約テストの戦略を**ソルバごとに規模で絞れる**ようにし、CP-SAT は小さな規模
  (タスク ≤ 6、ロボット ≤ 3)に限る。Hypothesis の `deadline` は CP-SAT 用に無効にする。
- **手作りシナリオの固定:** `greedy-trap` などで、CP-SAT の makespan が期待値(最適値)であることを
  テストに書く。
- 規模が大きいケースの時間制限到達(`feasible`)は、貪欲法のヒントにより
  **貪欲法以上の解が返ること**を、少数の例で確認する。

## Consequences

- (+) 最適な makespan(または証明つきの下界)が得られ、他のソルバの「最適からの距離」を測れる。
- (+) 全探索との一致テストと、他ソルバとの大小関係という、独立した検証の軸が増える。
- (+) 決定的時間の打ち切りで、時間制限に到達しても再現できる(同じ版・ビルド)。
- (−) **初めての外部依存。** wheel が大きく(数十MB)、CI のインストールが重くなる。
  OR-Tools の版更新で最適解の選ばれ方が変わりうるので、版は `uv.lock` で固定し、
  更新は PR で挙動(テスト)を確認する。
- (−) **スケールしない。** ロボットごとの circuit は変数が `ロボット数 × タスク数²` で増える。
  予備測定では、6台・20タスクの 40 シード中 15 で、20秒(壁時計)の上限までに最適性を証明できなかった
  (下の測定)。到達した場合は「最適」と言えず、ADR-0008 で `optimal` の割合を併記する。
- (−) 2段階にしても、**最適な Plan が一意とは限らない**。同点の選ばれ方は版・OSで変わりうる。
- (−) 契約テストの戦略を絞るため、CP-SAT は大きな規模では契約テストの対象外になる。
  補うのは「全探索との一致」と「他ソルバとの大小関係」。
- (−) 干渉・待ちがない単純な問題なので、CP-SAT の強み(時間窓・資源競合などの複雑な制約)は
  見えない。この問題での CP-SAT は「最適化の物差し」としての役割が主。

## Alternatives considered

- **MIP(大Mによる時刻変数)の定式化:** 時刻変数と大M制約が必要で、緩和が弱く遅い。
  待ちがない問題では、circuit の費用和で足りる。
- **区間変数 + `NoOverlap` + 遷移時間:** スケジューリングの定石だが、ロボットが干渉しないので
  資源競合がなく、過剰。
- **割当と巡回順を分けて解く(分解):** 簡単だが最適性が失われる。割当と順序が結合していることが
  この問題の本質なので、一緒に解く。
- **壁時計の時間制限:** 設定が直感的だが、負荷で解が変わる。決定性の方針に反する。
- **`num_workers > 1`:** 速いが、探索が非決定的になる(CLAUDE.md の方針に反する)。
- **重みつきの単一目的:** 上記。下界が使いにくい。
- **ハンガリアン法の解をヒントにする:** 貪欲法より良い解が多いが、ソルバ同士の依存が増える。
  ヒントは安全網なので、より単純な貪欲法にする。

## 予備測定

実装前の試作(makespan のみを最小化する単一段階。壁時計の上限20秒、`num_workers=1`)で、
生成シナリオ(シード 0 から連番)を解いた。ベンチマークではなく**実現可能性の目安**。
ADR-0008 で、本実装の 2 段階・決定的時間で測り直す。

| 設定 | シード数 | 最適性を証明 | 平均 makespan 貪欲 / ハンガリアン / CP-SAT | 貪欲・ハンガリアンの CP-SAT 比(平均の相対差) | CP-SAT の解く時間(平均 / 最大) |
|---|---|---|---|---|---|
| 4台・10タスク(既定) | 200 | 200 | 32.6 / 30.7 / 23.4 | +40.7% / +32.8% | 0.04秒 / 0.2秒 |
| 4台・15タスク | 100 | 100 | 48.3 / 42.7 / 32.0 | +51.9% / +34.8% | 0.30秒 / 1.7秒 |
| 6台・20タスク | 40 | **25** | 35.8 / 34.5 / 23.9 | +49.7% / +45.3% | 10.9秒 / 20秒(上限) |

- CP-SAT の makespan が貪欲法・ハンガリアン法を**下回らなかったシードはない**(同点はあり。既定で貪欲法と 8、
  ハンガリアン法と 11)。ADR-0005 で見えた「ハンガリアン法が完了時間で貪欲法に負けるシードがある」状況の外側に、
  大きな改善余地があることが分かった。
- ただし最適性の証明は、**15タスク・4台までは全件、20タスク・6台では約6割**。
  このあたりが CP-SAT の実用上限で、ベンチマークは 15 タスク前後までを主にする。
- 6台・20タスクで最適性が証明できなかった場合も、平均で貪欲法より 2 割以上良い解を返している。
  ただし最適からの距離は、下界が残るぶんだけ不確かになる。

## Routing の試作で分かったこと(ADR-0009 への引き継ぎ)

OR-Tools の Routing ライブラリを試作した(使い捨てのスクリプト。コードは残していない)。

- 開いた経路は「共通のダミー終端ノード」、ロボットごとの速度は車両ごとの遷移評価器、
  適格性は `VehicleVar(...).RemoveValue(...)` で表現できた(`SetAllowedVehiclesForIndex` は
  Python の list を受け付けなかった)。
- 結果は makespan が貪欲法より悪く(例: 既定のシード0〜3で 36/37/61/48。CP-SAT は 30/29/20/24)、
  かつ**解の目的関数値と時間次元の値が 0 と報告される**など、モデルの意味を誤っている疑いが残った。
  原因は未解決。
- よって Routing の採否は、**原因の切り分けを含めて ADR-0009 で別に決める**。
  本ADRの CP-SAT 実装は Routing に依存しない。

## 見直しの条件

- 20タスク前後で `optimal` の割合が低く(予備測定: 6台・20タスクで 25/40)、下界ギャップの議論が成り立たない
  (規模を絞る、決定的時間の上限を上げる、対称性の除去を入れる)。
- OR-Tools の更新で、同じ入力の最適値が変わる、または決定性が崩れる。
- CI のインストール時間・ビルド時間が許容できない(extras への分離を検討する)。
