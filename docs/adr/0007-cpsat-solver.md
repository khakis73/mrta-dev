# ADR-0007: CP-SAT ソルバ

- Status: Accepted
- Date: 2026-11-10

## Context

- Phase 3 の目的は「ソルバ拡充」と「下界ギャップ」(README)。これまでの貪欲法・ハンガリアン法は
  どちらも**ヒューリスティック**で、「最適解からどれだけ離れているか」が分からない。
  最適解(または証明つきの下界)を出せるソルバが、比較の物差しになる。
- ADR-0003 は、整数の問題として定義した理由に「CP-SAT が整数しか扱えず、下界を厳密に計算できる」ことを挙げた。
  本ADRはその前提を実装に落とす。
- 本ADRの範囲は **CP-SAT ソルバ(makespan 最小化)** まで。下界の定義とベンチマークは ADR-0008、
  Routing は ADR-0009 で別に決める(試作の知見は末尾)。
- 制約(ADR-0003、契約テスト): ソルバは `Scenario → Plan` の純関数、`kind` を見ない、
  ロボット順に依存しない、決定的。CLAUDE.md の方針: `num_workers=1`、制限は固定、整数のみ。
- **ここまで依存ゼロ**(`pyproject.toml` の `dependencies = []`)。初めて外部ライブラリを入れる。

## Decision

### 依存: OR-Tools を通常の依存に追加する

- `ortools` を `dependencies` に入れ、`uv.lock` で固定する(CI は `uv sync --locked`)。
- `mrta.solvers.cpsat` の先頭で import する。遅延 import や extras にはしない
  (`mrta publish` などからも使え、構成を単純に保つため)。
- 影響(実測・計測前提の見積り):
  - `import ortools.sat.python.cp_model` は約 0.3 秒。`SOLVERS` の import で毎回かかるので、
    CLI の起動とテストの収集が遅くなる。許容する。
  - インストールサイズは約 68MB(macOS / Python 3.12)。`ci.yml` の `uv sync --locked` は
    `uv` のキャッシュで緩和される。`pages.yml` は `uv sync --locked` で
    `mrta publish` の環境を作るため、そこでも取得が増える。
  - Linux(CI の ubuntu)向けの wheel(`manylinux`、cp312)が `uv.lock` に入ることを確認した。
  - 推移的な依存も増える(`numpy`、`pandas`、`protobuf`、`absl-py` など)。
  - `ortools` は `py.typed` を持つが、一部の API(`CpModel.clear_hints`)は型注釈がなく、
    mypy strict が通るよう、その1行だけ理由つきの `# type: ignore` にした。

### 定式化: ロボットごとの circuit 制約

ロボット `r` と、`r` に適格なタスクの集合 `E_r` ごとに、ノード `{0(開始位置)} ∪ E_r` の
**開いた経路**を `AddCircuit` で表す。

- アーク `i → j`(`j ∈ E_r`)のリテラル `x[r,i,j]`。費用は
  `travel_ticks(manhattan(i, j), r.speed) + service_time(j)`(ADR-0003 の実行の意味と同じ)。
- タスクを訪問しない場合は自己ループ `j → j`。訪問リテラル `v[r,j]` はその否定。
- **開いた経路**(帰還しない): 各ノード `i`(ノード0を含む)から「ノード0へ戻るアーク」を**費用0**で置く。
  `i` が最後のタスクなら、これが経路の終端になる。`i=0` のこのアークは、ノード0の自己ループ
  `0 → 0` そのもので、**何も訪問しないロボット**を表す。自己ループを別に足してはいけない
  (試作で二重になり `MODEL_INVALID` になった)。
- **未使用のロボットがタスクを巡る閉路を禁じる(必須):** `AddCircuit` は、ノード0の自己ループが真でも、
  ノード0を通らない別の閉路を許す。放置すると、未使用のはずのロボットが**出発位置からの移動なしに**
  タスクを巡れる(緩和モデル)。そのため、全ての訪問リテラルについて
  `v[r,j] ⇒ ¬x[r,0,0]` の含意を置く。
  試作で一度この制約を忘れ、**不正な Plan(未割当のタスク)と、誤って小さい目的値**が出た。
  性質上、最適値の「見かけ上の改善」になるため、テストの比較だけでは気づきにくい(テスト節)。
- 各タスクはちょうど1台に割り当てる: `Σ_r v[r,t] = 1`。
- ロボットの完了時刻 `f_r = Σ(アーク費用)`。**待ちがない**(ADR-0003)ので、これで足りる。
  時刻の変数やタスク間の大M制約は要らない。
- スキル・容量は、適格なロボットだけに変数を作ることで表す(`is_eligible` を使う)。
- **縁の扱い:**
  - タスクが0件、または `E_r` が空のロボットは、ノードがノード0だけの circuit になる。
    自己ループ1本だけの `AddCircuit` は受け付けられ、そのリテラルは真になる(試作で確認)。
    特別扱いせず、空の経路になる。`Plan` は全ロボットIDをキーに持つ(ADR-0003)。
  - 適格なロボットがいないタスクは、`require_solvable` で例外にする(他のソルバと同じ)。
  - 完了時刻の変数の上限は、貪欲法の `Plan` の makespan とする(実行可能解の値なので、最適値は超えない)。
    定数の `10^5` のような根拠のない上限は置かない。

### 目的: 2段階の辞書式最適化

1. **makespan を最小化**する(`max_r f_r`)。ここで得た値 `M*` と、探索が証明した下界を
   `CpSatResult` に残す(ADR-0008 の下界ギャップに使う)。
2. `max_r f_r ≤ M*`(段階1の解の値)を制約にして、**総移動距離**(マンハッタン距離の総和。
   指標と同じもの)を最小化する。

- 理由: makespan だけだと、律速でないロボットが無駄に動き回る最適解が返りうる。
  4つの指標のうち2つ(完了時間・総移動距離)を、定義どおりに順序づけて扱う。
- 重みつきの単一目的(`M×K + 距離`)にしない: 1回で解けるが、探索が返す下界が
  makespan と距離の混合になり、makespan の下界として使いにくい。
- 段階1が最適性を証明できなかった(`FEASIBLE`)場合も、段階2は得られた解の値を上限にして続ける。

### 決定性

- **入力の正規化:** ロボットとタスクを ID の辞書順に並べてからモデルを作る
  (`Scenario` の並びに依存しない。ハンガリアン法と同じ)。
- **設定を固定する:** `num_workers=1`、`random_seed=0`。
- **打ち切りは決定的時間で行う:** `max_deterministic_time`(CP-SAT が数える、マシン非依存の作業量)を使い、
  **壁時計の `max_time_in_seconds` は使わない**。
  壁時計だと、負荷によって打ち切り位置が変わり、解が変わりうる
  (予備測定: 壁時計1秒の打ち切りでは決定的時間が 1.28 / 1.29 とばらついた。
  同一マシンでは再現したが、境界上にあり保証できない)。
  決定的時間では同じ入力から同じ解が得られた。
- config は `{"num_workers": 1, "random_seed": 0, "det_time_limit_ms": …}`
  (ADR-0004: 整数。名前に `time` を含む設定は `_ms` で終える契約テストに合わせる。
  値は「決定的時間の秒 × 1000」で、壁時計のミリ秒ではない。docstring と本ADRに明記する)。
  段階ごとの上限とし、既定は 各5000(= 決定的時間5。根拠は「予備測定」)。
- **フォールバック:** 段階1の探索に、貪欲法の `Plan` を**ヒント**(`AddHint`)として渡す。
  打ち切られても実行可能解が残る(貪欲法以上の解)。
- **限界(正直に書く):** 同じ OR-Tools のバージョン・ビルドでの再現を保証する。
  最適解が複数あるとき、**どの最適解が選ばれるか**は、OR-Tools の版や OS で変わりうる。
  したがってテストは `Plan` の一致ではなく、**makespan と総移動距離の値**を検証する
  (同一プロセス内の再現性だけ、契約テストで `Plan` の一致を見る)。

### インタフェース

```python
@dataclass(frozen=True, slots=True)
class CpSatResult:
    plan: Plan
    status: Literal["optimal", "feasible"]  # optimal ⇔ makespan == makespan_bound
    makespan: int  # plan を ADR-0003 の意味で実行したときの完了時間(段階2の解の値)
    makespan_bound: int  # 段階1が証明した下界(optimal なら makespan と一致)

def solve_cpsat(scenario: Scenario, config: CpSatConfig = ...) -> CpSatResult: ...

class CpSatSolver:  # Solver プロトコル
    name = "cpsat"
    def solve(self, scenario) -> Plan:  # solve_cpsat(...).plan
```

- `Solver` プロトコル(`Scenario → Plan`)は変えない。ログの形式(ADR-0004)も変えない。
- `status` と下界は**ログには載せない**。ベンチマーク(ADR-0008)が `solve_cpsat` を直接呼んで使う。
- `SOLVERS["cpsat"]` に登録する。共通の契約テストはそのまま使える。
- **`mrta publish` の公開物には含めない。** 実装で、`publish` が `SOLVERS` の全件を公開していたため、
  登録するだけで1つの例に3つのログが出て、2画面比較の前提(ADR-0006)が崩れることが分かった。
  `PUBLISHED_SOLVERS = ("greedy", "hungarian")` に明示的に固定する。CP-SAT は、最適解が複数あるときの
  `Plan` が版・OSで変わりうる(上の限界)ため、バイト一致を前提にする公開ログ・golden にも向かない。
  公開するなら、ペアの出し方とあわせて別のADRで決める。

### テスト

- **モデルとシミュレータの一致(上のバグを検出する):** 解いた `Plan` を `simulate` したときの makespan と
  総移動距離が、`CpSatResult` の値(モデルの値)と**一致する**ことを、性質テストで全シナリオについて確認する。
  `solve_cpsat` の内部では検査しない(ソルバはシミュレータを知らない: ADR-0003)。
  モデルとシミュレータは別々に実行の意味を持つので、この突き合わせがモデルの誤りの検出器になる。
  含意制約を外す変異を入れると、この検査・全探索との一致・契約テストの3件が失敗することを確認した。
- **全探索との一致(正しさの根拠):** 小さなシナリオ(ロボット ≤ 3、タスク ≤ 5)で、全ての割当と順序を
  列挙した最適 makespan と一致する。同じ makespan の中で総移動距離も最小である。
- **オラクルとしての性質:** `optimal` のとき、他の全ソルバ(貪欲法・ハンガリアン法)の
  makespan が CP-SAT 以上である(property-based)。
- **契約テスト:** `SOLVERS` への登録で自動的に対象になる。ただし既存の戦略
  (最大30タスク・8台)は CP-SAT には重く、時間制限に到達して遅くなる。
  契約テストの戦略を**ソルバごとに規模で絞れる**ようにし、CP-SAT は小さな規模
  (タスク ≤ 6、ロボット ≤ 3)に限る。Hypothesis の `deadline` は CP-SAT 用に無効にする。
- **手作りシナリオの固定:** `greedy-trap` などで、CP-SAT の makespan が期待値(最適値)であることを
  テストに書く。
- 規模が大きいケースの時間制限到達(`feasible`)は、貪欲法のヒントとフォールバックにより
  **有効な `Plan` が返り、貪欲法以上であること**を、極端に短い上限(1ms〜500ms)の例で確認する。
  実装で、1ms のように前処理で予算が尽きる上限では段階2が解を返さないことが分かったため、
  その場合は**段階1の解(なければ貪欲法の解)を、値を計算し直して返す**フォールバックを入れた
  (例外にしない)。このときの下界は、探索が出した値(得られなければ 0)。

## Consequences

- (+) 最適な makespan(または証明つきの下界)が得られ、他のソルバの「最適からの距離」を測れる。
- (+) 全探索との一致テストと、他ソルバとの大小関係という、独立した検証の軸が増える。
- (+) 決定的時間の打ち切りで、時間制限に到達しても再現できる(同じ版・ビルド)。
- (−) **初めての外部依存。** wheel が大きく(数十MB)、CI のインストールが重くなる。
  OR-Tools の版更新で最適解の選ばれ方が変わりうるので、版は `uv.lock` で固定し、
  更新は PR で挙動(テスト)を確認する。
- (−) **スケールしない。** ロボットごとの circuit は変数が `ロボット数 × タスク数²` で増える。
  予備測定では、6台・20タスクの 40 シード中 10 で、各段階 20 秒の上限までに最適性を証明できなかった
  (5秒なら 24 件)。到達した場合は「最適」と言えず、ADR-0008 で `optimal` の割合を併記する。
- (−) 2段階にしても、**最適な Plan が一意とは限らない**。同点の選ばれ方は版・OSで変わりうる。
- (−) 契約テストの戦略を絞るため、CP-SAT は大きな規模では契約テストの対象外になる。
  補うのは「全探索との一致」と「他ソルバとの大小関係」。
- (−) 干渉・待ちがない単純な問題なので、CP-SAT の強み(時間窓・資源競合などの複雑な制約)は
  見えない。この問題での CP-SAT は「最適化の物差し」としての役割が主。

## Alternatives considered

- **MIP(大Mによる時刻変数)の定式化:** 時刻変数と大M制約が必要で、緩和が弱く遅い。
  待ちがない問題では、circuit の費用和で足りる。
- **区間変数 + `NoOverlap` + 遷移時間:** スケジューリングの定石だが、ロボットが干渉しないので
  資源競合がなく、過剰。
- **割当と巡回順を分けて解く(分解):** 簡単だが最適性が失われる。割当と順序が結合していることが
  この問題の本質なので、一緒に解く。
- **壁時計の時間制限:** 設定が直感的だが、負荷で解が変わる。決定性の方針に反する。
- **`num_workers > 1`:** 速いが、探索が非決定的になる(CLAUDE.md の方針に反する)。
- **重みつきの単一目的:** 上記。下界が使いにくい。
- **ハンガリアン法の解をヒントにする:** 貪欲法より良い解が多いが、ソルバ同士の依存が増える。
  ヒントは安全網なので、より単純な貪欲法にする。

## 予備測定

本ADRの設計(正規化 → 段階1 → 段階2、貪欲法のヒント、決定的時間、`num_workers=1`)どおりの試作で、
生成シナリオ(シード 0 から連番)を解いた。ベンチマークではなく**実現可能性の目安**。
ADR-0008 で、本実装で測り直す。

> **訂正:** この節の初版は、未使用ロボットの閉路を禁じる含意(上の「必須」)を欠いたモデルで測った値だった。
> そのモデルは緩和であり、Plan が不正(未割当のタスク)で、makespan も実際より小さく出ていた。
> 以下は修正後のモデルで、全 Plan の妥当性と「目的値 = シミュレータの makespan」を確認したうえでの値。

| 設定 | シード数 | 決定的時間(各段階) | makespan を証明 | 平均 makespan 貪欲 / ハンガリアン / CP-SAT | CP-SAT に対する相対差の平均 貪欲 / ハンガリアン | 平均 総移動距離 貪欲 / ハンガリアン / CP-SAT |
|---|---|---|---|---|---|---|
| 4台・10タスク(既定) | 100 | 5秒 | 100 | 34.2 / 31.5 / 24.9 | +39.3% / +27.9% | 111.3 / 88.5 / 75.3 |
| 4台・15タスク | 60 | 5秒 | 60 | 48.1 / 42.2 / 32.5 | +48.2% / +30.9% | 165.1 / 118.8 / 94.8 |
| 6台・20タスク | 40 | 5秒 | 16 | 35.8 / — / 24.9 | — | — |
| 6台・20タスク | 40 | 20秒 | 30 | 35.8 / 34.5 / 24.6 | +45.2% / +40.9% | 198.3 / 139.2 / 107.5 |

- CP-SAT の makespan が貪欲法・ハンガリアン法を**上回ったシードはない**(同点は 4台・10タスクで
  貪欲法と 4、ハンガリアン法と 10。他の設定では 0)。ADR-0005 で見えた「ハンガリアン法が完了時間で
  貪欲法に負けるシードがある」状況より、はるかに大きな改善余地がある。
- **証明の限界:** 15タスク・4台までは 5 秒で全件証明できた。20タスク・6台は 5 秒で 16/40、20 秒で 30/40。
  このあたりが CP-SAT の実用上限。ベンチマークは 15 タスク前後までを主にし、20 タスクは上限を上げる。
- **証明できなかった 10 件(20秒)**も、平均 makespan は貪欲法 35.5 に対し 24.2、下界は 21.6
  ((CP-SAT − 下界) / 下界 の平均が 12.1%)。解の品質は高いが、最適からの距離は最大でこの隙間だけ不確かになる。
- **2段階の効果:** 段階1のみ(makespan だけを最小化)と段階2後の平均総移動距離は、
  4台・10タスクで 89.3 → 75.3、4台・15タスクで 120.1 → 94.8、6台・20タスク(20秒)で 135.1 → 107.5。
  makespan が同じ最適解の中でも、移動距離に 16〜21% の差がある。2段階にする根拠になる。
- CP-SAT の総移動距離は、makespan を優先したにもかかわらず、**ハンガリアン法(総和最小化が狙い)より短い**
  (75.3 対 88.5 など)。ADR-0005 の「完了時間と移動距離のトレードオフ」は、
  ヒューリスティック同士の比較で生じたもので、最適解の側にはその対立が小さいことを示唆する
  (ただし1つの生成器・設定での観測であり、一般化しない)。
- 時間(壁時計・並列4プロセスでの参考値): 4台・15タスクは段階1が平均 0.3 秒・最大 2.0 秒、
  6台・20タスク(20秒)は段階1が平均 6.1 秒・最大 12.7 秒、段階2が平均 4.2 秒・最大 11.9 秒。

### 測定で分かった設計の修正

- **段階2で makespan が下がることがある。** 段階1が最適性を証明できずに打ち切られたとき、
  段階2が「`max_r f_r ≤ M*`」の制約の下で、より小さい makespan の解を見つけうる(6台・20タスク、5秒で観測)。
  よって `CpSatResult.makespan` は**段階2の解の makespan**であり、段階1の `M*` ではない。
- **`status` はソルバの状態ではなく `makespan == makespan_bound` で決める。**
  段階2の「最適」は、距離の最適性であって makespan の最適性ではない。
  `optimal ⇔ makespan == makespan_bound`、そうでなければ `feasible`。
- 決定的時間の既定は**各段階 5 秒**(15 タスクまでの全件証明に足りる)。20 タスク規模では、
  ベンチマーク側で設定を上げる(設定は `CpSatConfig` で変えられ、ログの config に残る)。

## Routing の試作で分かったこと(ADR-0009 への引き継ぎ)

OR-Tools の Routing ライブラリを試作した(使い捨てのスクリプト。コードは残していない)。

- 開いた経路は「共通のダミー終端ノード」、ロボットごとの速度は車両ごとの遷移評価器、
  適格性は `VehicleVar(...).RemoveValue(...)` で表現できた(`SetAllowedVehiclesForIndex` は
  Python の list を受け付けなかった)。
- 結果は makespan が貪欲法より悪く(例: 既定のシード0〜3で 36/37/61/48。CP-SAT は 30/29/20/24)、
  かつ**解の目的関数値と時間次元の値が 0 と報告される**など、モデルの意味を誤っている疑いが残った。
  原因は未解決。
- よって Routing の採否は、**原因の切り分けを含めて ADR-0009 で別に決める**。
  本ADRの CP-SAT 実装は Routing に依存しない。

## 見直しの条件

- 20タスク前後で `optimal` の割合が低く(予備測定: 6台・20タスクで 5 秒なら 16/40、20 秒なら 30/40)、下界ギャップの議論が成り立たない
  (規模を絞る、決定的時間の上限を上げる、対称性の除去を入れる)。
- OR-Tools の更新で、同じ入力の最適値が変わる、または決定性が崩れる。
- CI のインストール時間・ビルド時間が許容できない(extras への分離を検討する)。
