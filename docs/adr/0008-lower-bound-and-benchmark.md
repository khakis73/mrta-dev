# ADR-0008: 下界とベンチマーク

- Status: Accepted
- Date: 2026-11-10

## Context

- ADR-0003 は、指標の1つに「下界ギャップ = `(完了時間 − 下界) / 下界`」を挙げ、
  **下界の定義と計算は Phase 3 の別ADRで決める**とした。本ADRで決める。
- CLAUDE.md の方針: 1シナリオの勝ち負けで判断せず、**複数シードの統計と下界を併記する**。
  指標は完了時間・総移動距離・稼働率・下界ギャップの4つのみ。
- ADR-0007 で、CP-SAT が makespan の最適値、または証明つきの下界(`makespan_bound`)を返せるようになった。
  ただし最適性を証明できない規模があり(20タスク・6台で約3割)、そのときの下界は緩い。
- これまでの比較は、ADR-0005 の予備測定のように、使い捨てのスクリプトで取っていた。
  再現できる形(コマンド、固定のシード範囲、決定的な出力)にして、結論の根拠にしたい。
- 制約: 整数と決定性(ADR-0003・0004)。依存を増やさない(統計ライブラリは使わない)。
  **ベンチマーク結果は Pages に載せない**(スコープ。下の「公開しない」)。

## Decision

### 下界の定義

`LB(s) = max(LB_task(s), CP-SAT が証明した makespan の下界)`。

- **CP-SAT の下界:** `solve_cpsat(s).makespan_bound`(ADR-0007)。最適性を証明できれば最適値に一致する。
- **`LB_task`(ソルバ不要の床):** 各タスク `t` について、適格なロボットが**開始位置から直行して**作業を終える
  最短の時刻を考え、その全タスクでの最大値とする。

  ```
  LB_task(s) = max_t  min_{r が t に適格}  ( travel_ticks(manhattan(r.start, t.location), r.speed) + t.service_time )
  ```

  タスクが0件なら 0。**妥当性:** どの Plan でも `t` は適格なロボット `r` が実行し、`r` の完了時刻は
  `t` の完了時刻以上。経由すると移動時間は直行より短くならない
  (`ceil(a/v) + ceil(b/v) ≥ ceil((a+b)/v)` と三角不等式)ので、`t` の完了は上式以上になる。
- **`LB_task` を足す理由(正直に書く):** 予備測定では、**CP-SAT の下界を上回ったことは一度もない**
  (200シード。最適値との相対差 `(最適値 − LB_task) / LB_task` の平均は 55〜86%)。それでも残すのは次の2点。
  - CP-SAT の下界が弱い場合(決定的時間の上限が短い、前処理で予算が尽きる: 下界 0)の**床**になる。
  - ソルバに依存せず**どの規模でも**計算でき、全ソルバの makespan 以下であることを検証できる
    (ADR-0007 のテストは小さな規模に限られるため、大きな規模の妥当性検査に使う)。
- **作業時間の総和 ÷ ロボット数**の下界も試したが、`LB_task` との `max` が変わらず(効いていない)、
  採用しない。
- **保証の範囲:** ADR-0003 の問題(静的、干渉なし、帰還なし、累積容量なし)に対する下界。
  モデルを変えたら再検討する。

### 下界ギャップ

- 定義: `gap = (makespan − LB) / LB`。**厳密な分数(`Fraction`)**で持ち、浮動小数点にしない。
- `LB == 0` のときは未定義(`None`)。稼働率と同じ扱い(ADR-0003)。
- `makespan < LB` は**バグ**(モデルかソルバの誤り)。ベンチマークは例外にして止める。
- **読み方の注意:** LB は最適値以下なので、ギャップは**最適からの距離の上限**。
  最適性を証明できたシードでは `LB = 最適値` で、ギャップは真の最適からの距離になる。
  証明できなかったシードでは、LB が緩いぶんギャップが過大になる。
  よって**必ず「最適性を証明できたシードの割合」を併記する**。

### ベンチマーク: `mrta bench`

#### プリセット

名前つきの固定設定。シード範囲もプリセットが持つ(`0 .. n-1`)。

| プリセット | 生成器の設定 | シード数 | CP-SAT の上限(各段階) | 用途 |
|---|---|---|---|---|
| `small` | 4台・10タスク(既定) | 100 | 5秒 | 既定の規模。全件で最適性を証明できる |
| `medium` | 4台・15タスク | 60 | 5秒 | 全件で証明できる上限付近 |
| `large` | 6台(AMR 3 + マニピュレーター 3)・20タスク | 40 | 20秒 | 証明できないシードが残る規模 |
| `tiny` | 2台・5タスク | 3 | 5秒 | **テスト用**。CI で回せる速さ |

- 上限の根拠は ADR-0007 の予備測定。`--seeds N` でシード数を変えられる(先頭から N 件)。
- 対象ソルバは `SOLVERS` の全件。**CP-SAT は下界のために必ず走らせる**。

#### 1行ぶんの測定

シード × ソルバごとに、シミュレータの指標(ADR-0003)から**整数**で記録する。

`makespan`、`total_distance`、`busy_total`、`available_total`(稼働率は比にせず分子と分母。ADR-0004 と同じ)。
シードごとに `lower_bound`、`bound_proven`(CP-SAT が最適性を証明したか)も記録する。
**壁時計の時間は出力に含めない**(決定性を壊すため)。進捗と所要時間は標準エラーにだけ出す。

#### 集計(`bench.md`)

プリセットごと・ソルバごとに、**n とシード範囲を必ず併記**して表にする。

- 完了時間: 平均、中央値、90パーセンタイル(最近順位法)、最大
- 下界ギャップ: 平均、中央値、最大、**下界に一致した件数**(ギャップ 0)
- 総移動距離の平均、稼働率の平均(定義できるシードのみ)
- ベースライン(貪欲法)との**勝ち / 同点 / 負け**(完了時間が小さいほうが勝ち)
- 最適性を証明できたシードの割合

集計は `Fraction` で行い、表示のときだけ小数に直す(1桁、四捨五入は整数演算)。
numpy・pandas は使わない。**有意性検定や信頼区間は出さない**(下の限界)。

#### 出力

`mrta bench --preset small --out runs/bench-small` で次の2つを書く(`runs/` は `.gitignore` 済み)。
標準出力にも `bench.md` を出す。

- `bench.json`: 測定の生データ。整数のみ、キーをソート、空白なし(ADR-0004 と同じ規則)。
  `bench_version`(整数)、プリセットの設定、各ソルバの config、行の一覧、
  `environment`(`ortools` と Python の版)を持つ。**`environment` 以外は、同じ入力から同じバイト列になる。**
- `bench.md`: 上の集計。`bench.json` から決定的に作る。

`--jobs N` でシードを並列に解く(プロセス分割。各 CP-SAT は `num_workers=1` のまま)。
結果はシード順に並べるので、出力は `--jobs` に依存しない。既定は 1。

### 構成

- `mrta.bounds`: `task_lower_bound(scenario)`、`gap(makespan, bound)`。モデルだけに依存する。
- `mrta.bench`: プリセット、実行、集計、描画。ソルバとシミュレータに依存する。
- CLI に `bench` サブコマンドを足す。

### テスト

- **下界の妥当性(property-based):** 任意の生成シナリオ(大きな規模を含む)で、`LB_task` ≤ 全ソルバの makespan。
  小さな規模では、`LB_task` ≤ 全探索の最適値。
- **ギャップ:** `gap` の定義、`LB == 0` で `None`、`makespan < LB` で例外。
- **集計:** 手計算できる小さな行の集合で、平均・中央値・パーセンタイル・勝敗が期待値と一致する。
- **`tiny` プリセットの実行:** 2回実行して `bench.json` の `environment` 以外がバイト一致。
  整数のみであること、`--jobs` を変えても同じ結果になること、`bench.md` に n と証明割合が載ること。
- **CI:** `tiny` だけ。`small` 以上は手元で実行する(`medium`・`large` は分単位)。

### 公開しない

ベンチマーク結果は **Pages に載せない**。ビューアに表やグラフの画面を足すと題材の作り込みになり、
主目的(設計・テスト設計・CI/CD)から外れる。代表的な結果は、設定・シード範囲・ソルバの版を添えて
README に表で記録する(ADR-0005 の予備測定と同じ扱い)。公開する場合は別のADRで決める。

## Consequences

- (+) 再現できるコマンドと決定的な出力になり、「どのソルバがどれだけ良いか」が
  シード範囲・下界・証明割合つきで言える。
- (+) 下界ギャップが、最適性を証明できたシードでは真の最適からの距離になる。
- (+) 整数と `Fraction` だけで閉じ、依存が増えない。
- (−) **証明できなかったシードでは、ギャップが過大になる。** 特に `large` は約3割が該当。
  証明割合の併記で注意を促すが、数字だけを切り出されると誤読される。
- (−) `LB_task` は緩く、単独ではほぼ役に立たない。CP-SAT が使えない規模(さらに大きな問題)では、
  ギャップが大きく出て比較にならない。その規模は Phase 3 の範囲外とする。
- (−) 有意性を検定しない。差が小さいとき(例: 同点が多い、勝敗が拮抗)は、シード数を増やして
  勝敗の偏りを見る。検定が必要になれば別のADR。
- (−) 結果は**この生成器・この設定**に対するもの。一般化しない。ADR-0005 の予備測定が示した
  「ヒューリスティック同士のトレードオフ」も、設定で変わる。
- (−) `environment`(OR-Tools の版)で、時間切れのシードの結果が変わりうる。記録はするが、保証しない。

## Alternatives considered

- **CP-SAT の下界だけを使う:** 単純だが、予算が尽きたときに下界が 0 になる。床としての `LB_task` が安い。
- **LP 緩和や ラグランジュ緩和の下界:** 強い下界を作れるが、別のソルバと数学の導入が要り、
  学習対象(設計・テスト・CI/CD)から外れる。CP-SAT の下界で足りる。
- **「既知の最良解」からのギャップ:** 下界ではなく、最良解との差。最適からの距離の上限にならず、
  ADR-0003 の定義(下界ギャップ)とも違う。
- **ブートストラップ法の信頼区間:** 差の不確かさを示せるが、乱数と浮動小数点が入り、決定的な出力と相性が悪い。
  必要になってから導入する。
- **実行時間を出力に含める:** 性能比較には欲しいが、出力が毎回変わり、バイト一致の検査ができない。
  標準エラーに限る。
- **結果を Pages に載せる:** 上記のとおり公開しない。
- **pandas で集計:** 簡単だが、依存を足してまで要る集計ではなく、`Fraction` で厳密に持てない。
- **プリセットをファイルに置く:** 柔軟だが、設定が増えて管理が負担になる。コードの定数で足りる。

## 見直しの条件

- 下界が緩く、ギャップが比較の役に立たない(強い下界の導入を検討する)。
- 結果を公開したくなった(別のADRで、スキーマとビューアの範囲を決める)。
- モデルを拡張した(累積容量、帰還、動的到着など)。`LB_task` の妥当性を再検討する。
- OR-Tools の更新で、同じプリセットの最適値や証明割合が変わった。
