# ADR-0009: Routing ソルバ

- Status: Accepted
- Date: 2026-11-10

## Context

- README の Phase 3 は「CP-SAT、Routing、ベンチマーク、下界ギャップ」。CP-SAT(ADR-0007)は厳密解だが、
  15 タスク前後までしか最適性を証明できない(20 タスク・6 台で約 3 割が証明できない)。
  **大きな規模でも数秒で良い解を返す手法**が、比較に欲しい。
- OR-Tools には、車両経路問題(VRP)専用の Routing ライブラリがある(CP-SAT とは別のソルバ)。
  追加の依存は要らない(ADR-0007 で `ortools` を入れ済み)。
- ADR-0007 の時点の Routing 試作は、**解の目的関数値と時間次元の値が 0 と報告され、貪欲法より悪い解**を返し、
  採否を保留していた。本ADRの前に原因を切り分けた(下の「切り分けの結果」)。
- 制約(ADR-0003): ソルバは `Scenario → Plan` の純関数、`kind` を見ない、ロボット順に依存しない、決定的。
  CLAUDE.md の方針: 制限は固定、整数のみ。ADR-0007 で、打ち切りは壁時計に依存させないと決めた。

## 切り分けの結果(試作の不具合の原因)

**Python のコールバックが例外を投げ、その例外が握りつぶされて、費用 0 として扱われていた。**

- 試作のコールバックは、OR-Tools が内部的に呼ぶ**実際には通らない弧**
  (終端ノード・他車両の開始ノードに絡む遷移、番兵の無効な index)で `IndexError` / `OverflowError` を
  投げていた(記録した例外は 298 件)。例外は表に出ず、費用 0 になる。
  目的関数 0、累積時間 0、貪欲法より悪い解は、すべて「費用 0 で探索していた」ことの帰結。
- 確認: (a) 例外を 0 件にしたコールバック、(b) 遷移時間の**行列を事前計算して
  `RegisterTransitMatrix` に渡す**方式、のどちらでも同じ目的値になり、時間次元の終端の累積時間と
  シミュレータの makespan が一致した。最小の例(コールバックが全域関数)は最初から正しく動いていた。
- 教訓: **コールバックを書く方式は、例外が黙って費用 0 になる**。行列方式なら、コールバック自体が
  存在しないので、この種の不具合が起きない。

## Decision

### Routing ソルバ `routing` を採用する

`SOLVERS["routing"]` に登録する(契約テストとベンチマークの対象になる)。

### 定式化

- **車両 = ロボット**(ID の辞書順)。ノードは、タスク `0..n-1`、各ロボットの開始位置 `n..n+R-1`、
  **全車両で共通のダミー終端** `n+R`。タスクは ID の辞書順に並べる(`Scenario` の並びに依存しない)。
- **開いた経路**(帰還しない): 終端ノードへの遷移の費用は 0。
- **遷移時間は車両ごとの行列**: `travel_ticks(manhattan(from, to), robot.speed) + to.service_time`
  (ADR-0003 の実行の意味)。終端・開始ノードが絡む遷移は 0。`RegisterTransitMatrix` で登録し、
  弧の費用(`SetArcCostEvaluatorOfVehicle`)と時間次元(`AddDimensionWithVehicleTransits`、
  開始時刻は 0 に固定)の両方に使う。**Python のコールバックは使わない。**
- **適格性**(スキル・容量): 不適格な車両を `VehicleVar(...).RemoveValue(...)` で除く。
  `SetAllowedVehiclesForIndex` は Python の list を受け付けなかったため使わない。
  どのタスクも**必ず訪問する**(未訪問を許す disjunction は置かない)。
- **目的:** `Σ(弧の費用) + K × (時間次元の終端の累積時間の最大値)`。`SetGlobalSpanCostCoefficient(K)`。
  開始時刻が全て 0 なので、後者は makespan。`K = 100` を既定とする
  (試作で 100 と 10000 の結果は同一だった。調整不要)。
- **ADR-0007 との違い:** CP-SAT のような厳密な辞書式(makespan → 総移動距離)ではなく、
  **重みつきの和**。第 2 項は総移動**時間**(`ceil` 後の移動 + 作業)で、総移動距離そのものではない。

### 探索と決定性

- 初期解 `PATH_CHEAPEST_ARC`、局所探索 `GUIDED_LOCAL_SEARCH`、**打ち切りは解の数 `solution_limit = 300`
  と、分岐数 `branch_limit = 20000`**(`BranchesLimit` を探索モニタに足す)。
- **壁時計の `time_limit` は使わない。** 試作では、時間制限 500 ms の GLS が同じ入力で同じ解を返さない
  ケースがあった(6 台・20 タスクで 19/20 が再現。1 件は不一致)。解の数による打ち切りは、
  試作の全件(100 シード × 2 回)で同じ解になった。
- 入力の正規化(ID 順)により、`Scenario` の並びに依存しない。
- **分岐数の上限が必要な理由(実装で判明):** 解の数だけでは、探索空間が極端に小さい問題で**探索が終わらない**。
  タスクを実行できるロボットが 1 台しかいない場合(例: 操作タスクを担当できるのがマニピュレーターだけ)、
  改善解がほとんど出ず、300 個に届かない。契約テストの戦略で再現し(1 AMR + 1 マニピュレーター・1 タスク、など)、
  Python の `SIGALRM` では C++ の探索を止められなかった(サブプロセスで検出)。
  分岐数は決定的で、通常のケースは規模によらず約 1500〜2100 分岐(局所探索の作業は数えられない)で
  終わるので、`20000` は約 10 倍の余裕がある。上限に達しても、返る解は有効で再現できる
  (生成シナリオ 75 件 — 4×10・4×15・6×20・8×60 — で、上限 20000 と上限なしの結果は全件同一だった)。ハングしていたケースは 0.2〜0.55 秒で終わる。
- config は `{"first_solution": "path_cheapest_arc", "metaheuristic": "guided_local_search",
  "solution_limit": 300, "branch_limit": 20000, "span_cost_coefficient": 100}`(ADR-0004: 整数と文字列。名前に `time` を含む設定は
  置かないので、`_ms` の規則に触れない)。
- **限界:** 同じ OR-Tools の版・ビルドでの再現を保証する。**下界は返さない**(ヒューリスティック)。
  時間の安全網(壁時計)は置かない。60 タスクでも平均 3.6 秒・最大 5.0 秒で終わった。

### インタフェース

```python
@dataclass(frozen=True, slots=True)
class RoutingResult:
    plan: Plan
    makespan: int      # 時間次元の終端の累積時間の最大値(モデルの値)
    total_time: int    # 弧の費用の総和(モデルの値)

def solve_routing(scenario: Scenario, config: RoutingConfig = ...) -> RoutingResult: ...

class RoutingSolver:  # Solver プロトコル
    name = "routing"
    def solve(self, scenario) -> Plan:  # solve_routing(...).plan
```

- ソルバはシミュレータを知らない(ADR-0003)。`makespan` はモデル(時間次元)の値で、
  **シミュレータの makespan と一致することをテストで確かめる**。今回の不具合(費用 0)を検出できる。
- タスクが 0 件のときは、モデルを作らず空の経路を返す(試作ではこのケースを確かめていない。実装で確認する)。

### テスト

- **契約テスト:** `SOLVERS` への登録で対象になる。GLS は 1 例あたり数百 ms かかりうるので、
  CP-SAT と同様に**小さな規模に絞る**(`CONTRACT_SCENARIOS`)。
- **モデルとシミュレータの一致:** 任意のシナリオで、`RoutingResult.makespan` がシミュレータの makespan に一致する。
  非空のシナリオで `makespan > 0` であること(費用 0 の再発を直接検出する)。
- **CP-SAT をオラクルにする:** 小さな規模で、Routing の makespan ≥ CP-SAT の最適値(最適性を証明できたとき)。
- **手作りシナリオ:** `greedy-trap`・`skill-trap` で最適値(6、3)に到達する。
- **統計的な期待(固定シード):** `small` のシード 0〜9 で、Routing の makespan の平均が貪欲法より小さい。
  Routing は貪欲法より悪くならないことを**保証しない**ので、シード単位ではなく平均で見る。
- **ベンチマーク:** `mrta bench` は `SOLVERS` の全件を回すので、`routing` が自動で加わる。
  README の代表結果の表を更新する(下界は CP-SAT 由来のまま)。
- **終了の保証:** 適格なロボットが 1 台だけのシナリオで、探索が終わる(`branch_limit` の回帰テスト)。
- Routing は 1 例あたり数十〜数百 ms かかるので、性質テストの例数を 40 に絞る
  (契約テストは小さな戦略のまま 100 例)。

### 公開

`mrta publish` の公開物には含めない(ADR-0007 の `PUBLISHED_SOLVERS` を変えない)。

## 予備測定

切り分け後の試作(行列方式、スパン係数 100)で、生成シナリオ(シード 0 から連番)を解いた。
ベンチマークではなく**実現可能性の目安**。実装後は `mrta bench` で測り直す。
CP-SAT は各段階の決定的時間 20 秒。
**「CP-SAT 比」「最適と同じ」の基準は CP-SAT が返した makespan** で、6 台・20 タスクでは
最適性を証明できていないシードを含みうる(最適値より大きい可能性があり、その分 Routing の差は小さく出る)。

| 規模(シード数) | 変種 | 平均 makespan | CP-SAT 比 | 最適と同じ | 貪欲法より悪い | 同じ入力で同じ解 |
|---|---|---|---|---|---|---|
| 4 台・10 タスク(50) | 貪欲降下 | 26.0 | +5.2% | 29 | 2 | 50/50 |
| | **GLS + 解数 300** | 25.0 | +1.1% | 45 | 0 | 50/50 |
| | GLS + 時間 500 ms | 24.8 | +0.2% | 48 | 0 | 50/50 |
| 4 台・15 タスク(30) | 貪欲降下 | 33.9 | +7.4% | 7 | 0 | 30/30 |
| | **GLS + 解数 300** | 32.2 | +1.5% | 21 | 0 | 30/30 |
| | GLS + 時間 500 ms | 32.1 | +1.4% | 22 | 0 | 30/30 |
| 6 台・20 タスク(20) | 貪欲降下 | 26.2 | +8.5% | 3 | 0 | 20/20 |
| | **GLS + 解数 300** | 24.8 | +2.2% | 14 | 0 | 20/20 |
| | GLS + 時間 500 ms | 24.8 | +2.2% | 14 | 0 | **19/20** |

(参考: 平均 makespan の CP-SAT / ハンガリアン法 / 貪欲法は、4×10 が 24.8 / 30.9 / 33.7、
4×15 が 31.7 / 41.0 / 47.8、6×20 が 24.2 / 33.9 / 34.3。)

- GLS(解数 300)は、最適値との差が平均 1〜2%、所要時間は平均 0.2〜0.6 秒。
  貪欲降下は一瞬(0.00〜0.02 秒)だが、差が 5〜9% 残る。
- **大きな規模**(8 台・60 タスク・格子 40×40、10 シード): Routing の平均 makespan 64.0、
  貪欲法 117.2、ハンガリアン法 98.1。**10 件すべてで両者を下回り**、所要時間は平均 3.6 秒・最大 5.0 秒。
  CP-SAT は最適性を証明できない規模で、最適値との比較はできない。
- ADR-0007 の「貪欲法より悪い」という試作の観測は、費用 0 で探索していたため。直したあとは成り立たない。

### 実装後の `mrta bench`(README に表で記録)

実装したソルバで測り直した(`small` 100 シード、`medium` 60 シード、`large` 40 シード)。
下界は CP-SAT 由来。最適性を証明できたシードは 100/100、60/60、29/40。

| プリセット | 平均完了時間 CP-SAT / Routing / ハンガリアン / 貪欲 | Routing の下界ギャップ 平均 / 最大 | 下界に一致 |
|---|---|---|---|
| `small` | 24.9 / 25.0 / 31.5 / 34.3 | 0.7% / **36.4%** | 93/100 |
| `medium` | 32.6 / 33.0 / 42.3 / 48.1 | 1.5% / 14.3% | 44/60 |
| `large` | 24.7 / 25.1 / 34.5 / 35.8 | 4.7% / 19.0% | 21/40 |

- 平均では最適に近いが、**最悪ケースでは離れる**(`small` で最大 36.4%)。ヒューリスティックの性質で、
  README に明記する。貪欲法に負けたシードは、3 プリセット(計 200 シード)で 0 件。
- 3 ソルバ(CP-SAT・ハンガリアン法・貪欲法)の行は、Routing の追加前後で一致した(決定性の確認)。

## Consequences

- (+) 大きな規模でも数秒で、最適値に近い解を返す。CP-SAT(厳密・小〜中規模)との対比ができる。
- (+) 行列方式でコールバックの例外問題が起きない。モデルの値とシミュレータの突き合わせで、
  同種の不具合を検出できる。
- (+) 追加の依存がなく、`SOLVERS` への登録で契約テストとベンチマークの対象になる。
- (−) **最適性を保証せず、下界も返さない。** 下界ギャップ(ADR-0008)は CP-SAT 由来の下界で測る。
  CP-SAT が証明できない規模(例: 60 タスク)では、下界が緩く、ギャップは大きく出る。
- (−) 貪欲法より悪い解を返す可能性を排除できない(観測では 0 件)。保証せず、平均で見る。
- (−) 目的が重みつきの和で、makespan の厳密な優先ではない。係数 100 と 10000 では同じ結果だったが、
  規模・時間のスケールが違えば変わりうる。
- (−) 同じ OR-Tools の版・ビルドでの再現のみ。版が変わると、探索の経路が変わり、解が変わりうる。
  テストは `Plan` の一致ではなく、makespan の不等式とモデルとの一致を見る。
- (−) 1 つの生成器・設定での予備測定。60 タスクには最適値の参照がなく、優位は「貪欲法・ハンガリアン法に対して」。
- (−) 契約テストを含めた pytest の実行時間が伸びる(約 13 秒 → 約 54 秒)。Routing は 1 例あたり
  数十〜数百 ms かかるため。許容できなくなれば、`branch_limit` を下げるか例数を減らす。
- (−) **OR-Tools の Routing は、Python のバインディングに癖が多い**(コールバックの例外、
  `SetAllowedVehiclesForIndex`、モデルを閉じる前の `GetArcCostForVehicle` でクラッシュする、など)。
  実装のコメントに残す。

## Alternatives considered

- **Python のコールバックで遷移時間を渡す:** 書きやすいが、例外が費用 0 になる。行列方式にする。
  (全域関数にすれば動くが、書き手の注意に依存する。)
- **壁時計の `time_limit` で打ち切る:** 設定が直感的だが、再現しないケースがあった(19/20)。
  ADR-0007 の方針と合わない。
- **貪欲降下(メタヒューリスティックなし):** 決定的で一瞬だが、最適値との差が 5〜9% 残る。
  GLS が 0.2〜0.6 秒で 1〜2% に縮める。
- **他のメタヒューリスティック(シミュレーテッドアニーリング、タブーサーチ)や LNS の調整:**
  GLS で十分良く、調整は題材の作り込みになる。
- **disjunction でタスクを落とせるようにする(ペナルティつき):** 全タスクを必ず割り当てる
  (ADR-0003)ので不要。
- **Routing を採用しない:** CP-SAT と貪欲法・ハンガリアン法だけでも比較は成立する。ただし、
  規模が大きいと CP-SAT が証明できず、「大きな規模での比較」ができなくなる。
- **ペナルティではなく makespan を厳密に優先する 2 段階にする:** Routing では 2 回解く必要があり、
  係数を変えても結果が同じだったので、複雑さに見合わない。

## 見直しの条件

- 規模を上げると、探索が長くなる(所要時間が許容を超えたら、`solution_limit` の見直しや、安全網の時間制限を検討する。決定性とのトレードオフ)。
- OR-Tools の更新で、同じ入力の解や所要時間が変わる、または決定性が崩れる。
- 貪欲法より悪い解が、実測で目立つ頻度で出る(係数や初期解を見直す)。
- モデルを拡張した(待ち時間、時間窓、累積容量など)。Routing は時間窓や累積容量に強いので、再評価する。
