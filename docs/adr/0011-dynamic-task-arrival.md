# ADR-0011: 動的なタスク到着(モデル・実行の意味・ログ・生成器)

- Status: Accepted
- Date: 2026-11-10

## Context

- Phase 4 は「動的: ローリングホライズン」だけになった(ADR-0010)。ADR-0003 は静的な問題
  (全タスクが時刻0で既知)として定義し、「Phase 4 で動的なタスク到着を使う。モデルはそれに
  拡張できる形にしておく」とした。ADR-0004 も、実行中に行が増える場合に備えて追記しやすい形にした。
- 動的な問題の核は、**タスクが途中で現れ、ロボットはそれを到着まで知らない**こと。これをモデルに入れる。
- ローリングホライズン(到着のたびに既知のタスクで解き直す)は、モデルと実行の意味が決まってから設計する。
  本ADRは、その土台(モデル、実行の意味、指標、ログ、生成器、下界)を決める。
- 制約: 整数と決定性(ADR-0003・0004)。静的なシナリオ(全タスクの `release_time` が0)の結果とログは、
  **バイト単位で変えない**(既存の golden file がそのまま通る)。
  1シナリオの勝ち負けでなく、複数シードの統計と下界で見る(CLAUDE.md)。

## 予備測定(実現可能性)

実装前の使い捨ての試作で、4台・10タスクの生成シナリオ(シード 0〜59)に、一様な到着時刻
`release_time ∈ [0, W]` を付けた。実行の意味は下記の Decision と同じ。
静的ソルバは**到着を無視して**解いた Plan を、この実行の意味で評価した。
「簡易ローリング」は、到着順にタスクを知り、知った時点で完了時刻が最小になるロボットの末尾へ追加する
貪欲法(再最適化なし)。ベンチマークではなく**実現可能性の目安**。

| 到着の窓 W | 最後の到着(平均) | 平均 makespan: CP-SAT / Routing / ハンガリアン / 貪欲(静的、到着を無視) | 簡易ローリング | 簡易な下界(平均) |
|---|---|---|---|---|
| 0(静的) | 0.0 | 24.5 / 24.7 / 30.9 / 33.5 | 33.5 | 17.1 |
| 10 | 9.5 | 31.0 / 31.0 / 37.0 / 39.4 | 34.6 | 17.6 |
| 20 | 18.8 | 38.9 / 38.8 / 43.5 / 46.0 | 38.4 | 23.0 |
| 40 | 36.9 | 55.6 / 55.4 / 58.5 / 61.7 | 50.9 | 40.4 |
| 80 | 73.2 | 90.7 / 90.4 / 93.3 / 95.4 | 84.8 | 76.5 |

- **到着を無視した静的な計画は、動的では大きく劣化する。** 静的に最適な CP-SAT でも、W=20 で makespan が
  24.5 から 38.9 に伸びる。
- **到着を知ってから割り当てる簡易ローリングが、W ≥ 20 で、静的な最適(CP-SAT)の計画を下回る。**
  (W=40 で 50.9 対 55.6。W=20 でも 38.4 対 38.9。)「静的に最適」は動的では最適ではない。
  到着を考慮した扱いが、ソルバの最適性より効く。
- **W が大きいと差が潰れる。** W=80 では makespan が「最後の到着 + 作業」に支配され、ソルバ間の差が
  約 5.5% に縮む(W=0 では約 37%)。比較に使うなら、W は静的な makespan(約 25〜30)の半分程度まで。
- 稼働率は W とともに大きく下がる(W=0 で 0.79、W=40 で 0.35。待機が増えるため)。
- **簡易な下界は弱い。** W=20 で 23.0 に対し、達成されている値は 38 前後。強い下界は別に要る(下記)。

## Decision

### モデル: タスクに到着時刻 `release_time` を足す

- `Task.release_time: int`(0 以上の整数ティック、**既定 0**)。タスクは `release_time` に現れる。
  静的なシナリオは全タスクが 0 で、これまでと完全に同じ。
- `Plan`(ロボットごとの実行順)は**変えない**。待ちの時刻などを `Plan` に持たせない。

### 実行の意味(ADR-0003 の「待ちなし」を更新する)

ロボットは、`Plan` の順に「(待機)→ 移動 → 作業」を行う。

- 各タスクの**移動の開始時刻 = max(直前の完了時刻, そのタスクの `release_time`)**。
  最初のタスクでは、直前の完了時刻を 0 とする。
- 待つのは**出発前だけ**。`release_time` より前に、そのタスクへ**先回りして移動することはできない**
  (到着まで、タスクの存在を知らないため)。
- ロボット同士は干渉しない。ロボットの完了時刻は、**自分の経路と、その経路のタスクの到着時刻だけ**で決まる
  (ADR-0003 の独立性は保たれる)。タスクが0件のロボットの完了時刻は0。
- 指標: 完了時間は全ロボットの完了時刻の最大値。**稼働時間(`busy`)は移動と作業だけ**で、待機を含まない。
  `available_total = ロボット数 × 完了時間` は変えないので、**待機が増えると稼働率が下がる**。
  総移動距離は変わらない。
- `release_time = 0` の全タスクでは、待機が生じず、従来の結果と一致する(回帰テストで確認する)。

### 静的ソルバの扱い

- ソルバの契約(`Scenario → Plan`)は**変えない**。既存のソルバ(貪欲法・ハンガリアン法・CP-SAT・Routing)は
  `release_time` を**見ない**。有効な `Plan` を返すが、待機を考慮しない静的な最適化をする。
  「到着を無視した静的な計画」を、動的の評価でそのまま測れる(上の予備測定)。
- したがって、動的なシナリオでの CP-SAT の makespan は**最適ではない**。報告では、静的ソルバの結果を
  「静的(到着を無視)」と明記し、ローリングホライズン(次のADR)と区別する。
- **静的ソルバの結果は「オンライン」の基準ではない。** 静的ソルバは到着時刻を見ないが、
  **未来のタスクの存在と場所を時刻0で知っている**(シナリオ全体を受け取るため)。
  実行時は先回りできない(上の実行の意味)ので、オフラインの最適でもない。位置づけは
  **「割当と順序は未来を知って決め、移動は到着を待つ」中間の基準**とする。
  - 予備測定の「簡易ローリングが静的な最適の計画を下回る」は、この非対称な比較である
    (簡易ローリングは未来を知らないのに勝つ、という意味で、到着を考慮する価値を示す)。
  - ベンチマークでは、静的ソルバの行を「静的(未来を知った順序、到着は無視)」と表示し、
    オンライン(ローリングホライズン)・オフライン(到着時刻つきの最適)と並べて区別する。

### ログ(ADR-0004、スキーマは v1 のまま)

- `scenario` 行の各 `tasks[]` に、**`release_time`(整数・0 以上)を足す**。後方互換な追加なので
  `schema_version` は上げない。読む側は、無ければ 0 とみなす。
- 書き出しは、**`release_time` が 0 のとき書かない**(正のときだけ書く)。
  - 静的なシナリオのログは**バイト単位で従来と同じ**になり、既存の golden file の一致が、
    そのまま「静的な問題に影響がない」ことの回帰テストになる。
  - 読む側の「無ければ 0」は、公開済みの古いログのためにどのみち必要なので、常に書いても読む側の分岐は減らない。
    書く側の分岐は1か所で済む。
  - JSON Schema では `release_time` を任意のフィールド(整数・0 以上)として足す。
  - 動的なシナリオの golden file を1つ足し、`release_time` を書く経路を検証する。
- `segment` の並び(`t0`、ロボットID、`kind`)は変えない。**待機はセグメントにしない**(時間の隙間として現れる)。
  ビューアは、隙間を「直前の終点で待機」として扱える(`robotStateAt`)。ログの検証も隙間を禁じていない。
- 新しい行の種類(到着イベントなど)は足さない。到着はシナリオの `release_time` から分かるため。
- `metrics` は変えない。

### 生成器

- `GeneratorConfig.arrival_window: int`(**既定 0**)。0 なら静的(全タスクの `release_time` は 0)。
  正なら、各タスクの `release_time` を `rng.randint(0, arrival_window)` で引く。
- **乱数の引く順序は契約**(`mrta.scenario`)なので、`release_time` の抽選は、**既存の抽選
  (ロボット、タスク)の後に、別のループでタスクID順に引く**。`arrival_window = 0` のときは何も引かない。
  よって、静的なシナリオと、動的なシナリオの `release_time` 以外の項目は、シードごとに変わらない。
- ベンチマークの動的プリセットの窓は、予備測定から、静的な makespan の半分程度(例: 4台・10タスクで 20)とする。
  具体的な値は、プリセットを決めるときに ADR-0012 以降で決める。

### 下界

- **静的な下界は、動的でも有効。** 到着時刻は開始を遅らせるだけなので、動的な最適値は静的な最適値以上。
  CP-SAT の下界(`makespan_bound`)と `LB_task` は、そのまま下界として使える(ADR-0008)。
- **ただし弱い。** 到着を使った簡易な下界として、`LB_dynamic = max(LB, max_t(release_time(t) + service_time(t)))`
  を足せる(タスク `t` の完了は、到着 + 作業時間以上)。予備測定のとおり、これでも W=20 で 23.0 と、
  達成値(38 前後)に遠い。
- 強い下界は、**到着時刻つきの CP-SAT(オフラインの最適、全タスクを事前に知る)**で得られる。
  ロボットごとの時刻変数が要り、ADR-0007 の定式化の拡張になるため、**別のADRで決める**。
  ただし実装が重いため、**任意の項目**とし、ローリングホライズン(ADR-0012)の結果を見てから採否を決める。
  採用しない場合、動的の下界ギャップは `LB_dynamic` による**参考値**(大きく出る)と明記して報告する。
  これは「オンラインの結果と、先読みできるオフラインの最適」の比(競争比)を測る基準にもなる。

### この後の分け方(本ADRの範囲外)

| 順 | 内容 |
|---|---|
| 1 | 本ADR → 実装: `release_time`、シミュレータ、ログ・スキーマ・golden、生成器 |
| 2 | ADR-0012: ローリングホライズン(解き直しのタイミング、確定するタスクの規則、ソルバへの要求 `ready_at`) → 実装・ベンチマーク |
| 3 | (任意)ADR-0013: 到着時刻つきの CP-SAT(オフラインの最適)と、動的の下界。ADR-0012 の結果を見て採否を決める |
| 4 | ビューア: 到着前のタスクの表示、到着の印(必要なら ADR) |

ローリングホライズンは、ロボットの状態(位置、空く時刻)を実行の意味に従って追う必要があるため、
`Scenario → Plan` のソルバではなく、**シミュレーションの層にある「駆動役」**として設計する想定(ADR-0012)。

## Consequences

- (+) 静的なシナリオの結果・ログは変わらない(`release_time = 0`)。既存のソルバ・ベンチマークがそのまま動く。
- (+) `Plan` とソルバの契約を変えずに、動的な問題を表せる。
- (+) 到着を無視した静的ソルバを、動的の評価でそのまま測れ、「到着を考慮することの価値」が数字で見える。
- (−) **ADR-0003 の「待ちなし」前提を、「出発前の待機のみ」に緩める。** 稼働率の意味が変わり、
  待機は稼働に含まれない。静的な結果との比較では、この違いに注意する。
- (−) 動的なシナリオでは、既存の静的ソルバの結果は最適ではなく、CP-SAT の「最適性の証明」も
  動的な最適を意味しない(静的な最適の証明)。ベンチマークの表示で混同しないようにする。
- (−) **窓が大きいと差が潰れる**(makespan が最後の到着に支配される)。窓の選び方が結論を左右する。
  複数の窓で測り、窓を併記する。
- (−) 簡易な下界が弱く、動的では下界ギャップが大きく出る。強い下界は後続のADRで決める。
- (−) スキーマとビューアの型を更新する必要がある(後方互換な追加のため、既存のビューアは壊れない)。
  静的なシナリオの golden file は変わらない。
- (−) ログに `release_time` が「無い」場合と「0」の場合の2つの書き方がありうる。書く側は0を書かない規則に固定し、
  読む側はどちらも0として扱う。
- (−) 到着時刻が一様乱数というのは、1つの生成器の仮定。現実の到着(バースト、周期性)は表さない。

## Alternatives considered

- **作業の開始が `release_time` 以降であればよく、先回りして移動してよい:** オフラインの最適には有利だが、
  オンラインでは到着前にタスクを知らないので、先回りできない。オンラインとオフラインを同じ実行の意味で
  比べられなくなる。
- **到着をログの行(イベント)にする:** 追記しやすい形だが、シナリオの `release_time` と二重になる。
  静的な読み方(シナリオから全て分かる)が崩れる。
- **`Plan` に待機の時刻を持たせる:** ソルバが時刻まで決めることになり、契約(順序だけ)と実行の意味の
  分離が崩れる。待機はシミュレータが決める。
- **到着を浮動小数点・指数分布(ポアソン到着)にする:** 現実的だが、整数と決定性の方針(ADR-0003)に反する。
  整数の一様乱数で足りる。
- **時間窓(`release_time` と期限)を入れる:** 期限を守るかという別の問題になり、指標(4つ)も増える。
  到着時刻だけにとどめる。
- **静的ソルバにも `release_time` を理解させる(全ソルバを改修):** 各ソルバの改修が大きく、
  静的ソルバの結果が「到着を無視した計画」という分かりやすい基準でなくなる。
  到着の考慮は、ローリングホライズンの側で行う。

- **ログに常に `release_time` を書く(0 も書く):** 形が1つになるが、静的なシナリオの golden file が
  全て変わり、「静的な問題に影響がない」ことをバイト一致で示せなくなる。読む側は古いログのために
  「無ければ0」を持つ必要があり、分岐も減らない。

## 見直しの条件

- 窓を変えても、ソルバ間の差がほとんど出ず、比較の意味が薄い(窓の定義や、指標の見直し)。
- 待機を稼働率に含めるべき、または待機を別の指標にしたくなった。
- 到着の現実的なパターン(バースト、周期)を扱う必要が出た。
- 期限や優先度を入れる(時間窓、別の目的関数)。
