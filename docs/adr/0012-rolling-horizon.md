# ADR-0012: ローリングホライズン

- Status: Accepted
- Date: 2026-11-10

## Context

- ADR-0011 で、タスクに到着時刻 `release_time` を足し、「出発前の待機のみ」という実行の意味を決めた。
  既存の静的ソルバは到着時刻を見ない。
- Phase 4 の目的は、**到着を知ってから決めるオンラインの手法**(ローリングホライズン: 到着のたびに、
  既知で未確定のタスクを静的ソルバで解き直す)を、静的ソルバと並べて比べること。
- ADR-0011 の積み残し:
  - 解き直しのタイミング、確定するタスクの規則、ソルバへの要求(`ready_at`)。
  - 動的の強い下界(到着時刻つきの CP-SAT = オフラインの最適)を作るか。
- 制約(ADR-0003・0011): ソルバは `Scenario → Plan` の純関数、決定的、`kind` を見ない。
  静的なシナリオの結果とログはバイト単位で変えない。依存は増やさない。

## 予備測定

試作(`ready_at` を4つのソルバに入れ、駆動役を書いた使い捨てのコード)で測った。
ベンチマークではなく**実現可能性の目安**。実装後は `mrta bench` で測り直す。

### 前提の検証

- `ready_at` を入れた CP-SAT と Routing で、ばらばらの `ready_at` のシナリオ 40 件について、
  モデルの値(makespan、総移動距離、総稼働時間)とシミュレータの値が**全件一致**した。
- 駆動役が内部で追う完了時刻と、`simulate` の完了時刻が、160 件(40 シード × 窓 2 × ソルバ 2)で**全件一致**した。

- **ローリングは、窓が長い(W ≥ 20)と、全ソルバで makespan を縮める。**
- **W=10 では、強いソルバ(Routing・CP-SAT)は、ローリングのほうが悪い。** 静的は未来のタスクを
  知って順序を決められるため、窓が短いとそちらが有利になる(上の非対称)。
- **ソルバ間の差が縮む。** ローリングの4ソルバの makespan の幅は、W=10 で約 12%、W=20 で約 5%、
  W=40 で約 1.6%(静的は W=20 で約 21%)。ソルバの最適性より、**情報の入り方と確定の規則**が支配的になる。
- **総移動距離は、強いソルバでは増える**(CP-SAT で W=20 のとき 76.8 → 97.8)。その場その場で解くため。
  稼働率は、待機が減って上がる。
- 所要時間: 解き直し ≈ 9 回で、Routing が 1 インスタンスあたり約 0.3 秒、他は 0.03 秒以下。

makespan の比の平均。

|---|---|---|---|---|---|
| 20 | 31.9 | greedy | 1.226 | **1.087** | 26/60 |
| | | hungarian | 1.161 | **1.083** | 30/60 |

| | | cpsat | 1.090 | **1.058** | 36/60 |

- W=10 では、ローリングの比は 1.043〜1.109、W=40 では 1.046〜1.055(静的は W=10 で 1.036〜1.228、
  W=40 で 1.104〜1.192)。
  **ローリングは、この小さな規模では、オフライン最適の 1.05〜1.1 倍に収まる。**
  ローリングの最悪の比は 1.36〜2.00(W=10 の hungarian が 2.00)。
- 4台・10タスクでの簡易な下界(`LB_task`)は、W=20 で平均 22.4。達成値(36 前後)に遠く、

## Decision

### 1. ロボットの空く時刻 `ready_at`

- `Robot.ready_at: int`(0 以上、**既定 0**)。「このティックまで出発できない」。
- 実行の意味: **タスクが1つ以上あるロボットだけ**、`ready_at` から始める(`now = ready_at`)。
  **タスクが0件のロボットの完了時刻は 0 のまま**(ADR-0003)。`ready_at` 自体は完了時刻にならない。
- ログ: `robots[].ready_at` を**正のときだけ書く**(`release_time` と同じ規則。ADR-0011)。
  スキーマに任意のフィールドとして足す。通常のシナリオ(生成器)では常に 0 で、ログは変わらない。
  `ready_at` が正になるのは、駆動役が作る**解き直しの入力**(ログには出ない)。
- ビューアは `readyAt` を読む(無ければ 0)。表示は変えない。
- 下界: `task_lower_bound` の直行の時刻に `ready_at` を足す。ロボットがそのタスクを何番目に行っても、
  完了は `ready_at + 直行` 以上(出発は `ready_at` 以降で、経由しても移動時間は直行より短くならない。
  ADR-0008 と同じ論法)。ロボットごとの `min` を取る点は変わらない。

### 2. ソルバの対応(契約を変えず、`ready_at` を見る)

試作で4つとも対応でき、モデルの値とシミュレータが一致した。

| ソルバ | 対応 |
|---|---|
| 貪欲法・ハンガリアン法 | ロボットの初期の完了時刻を `ready_at` にする |
| CP-SAT | 開始ノードから出る弧の時間に `ready_at` を足す。完了時刻は弧の和なので、未使用ロボットは 0 のまま(追加の変数は要らない)。貪欲法のヒント・上界の計算にも `ready_at` を入れる |
| Routing | **時間次元の遷移**にだけ、開始ノードから出る弧に `ready_at` を足す(弧の費用 = 移動 + 作業は変えない)。空の経路の終端の累積時間は 0 のまま |

- `Solver` プロトコル(`Scenario → Plan`)とログの形式は変えない。
- 契約テストに `ready_at` を含めた戦略を足す。性質: 全ロボットの `ready_at` を一律に `k` だけ増やすと、
  貪欲法・ハンガリアン法は同じ `Plan`、CP-SAT は makespan が `k` 増える(タスクが1件以上あるとき)。

### 3. 駆動役 `RollingSolver`

- **`Solver` プロトコルを満たすクラスとして実装する**(`Scenario → Plan` の純関数)。内部でロボットの状態を
  追うが、結果は `Plan` だけ。よって、契約テスト・CLI・ログ・ベンチマークにそのまま載る。
- 基底のソルバ(`greedy`・`hungarian`・`cpsat`・`routing`)を受け取る。

**アルゴリズム**(試作で検証済み):

1. **エポック** = タスクの到着時刻(重複を除いて昇順)。
2. エポック `T` で、まず**確定**する: 各ロボットの待ち行列の先頭から順に、**出発時刻が `T` より前**のタスクを
   確定する(出発 = `max(ロボットが空く時刻, 到着)`)。確定したタスクは、ロボットの位置と空く時刻を進める。
   `T` ちょうどに出発するタスクは**確定しない**(`T` の時点の情報を使って解き直せる)。
3. **解き直す**: 未確定のタスク(待ち行列にあるもの + `T` までに到着したもの)を、静的ソルバに渡す。
   入力は、ロボットの `start` = 確定したタスクの終点、`ready_at` = `max(空く時刻, T)` のシナリオ
   (タスクの `release_time` は 0 にする。全て既知)。得た `Plan` で待ち行列を置き換える。
4. 最後のエポックの後、残りの待ち行列を全て確定する。結果の `Plan` = 確定した順序。

- 解き直しは**到着時刻のたびだけ**(ロボットが空いたときには解き直さない)。最大でタスク数回。
- 確定したタスクは変えない(**移動の途中で行き先を変えない**。先取りもしない)。
- 実行の式(出発・移動・作業)を駆動役が持つ(貪欲法と同じ二重実装)。**結果の `Plan` を `simulate` したときの
  各ロボットの完了時刻が、駆動役の内部の時刻と一致する**ことをテストで確かめる(試作で全件一致)。
- 決定性: ID 順に正規化し、基底のソルバが決定的なら、結果も決定的。
- 解き直しの対象に適格なロボットがいないタスクは、基底のソルバが例外にする(`require_solvable`)。

**登録と名前**:

- `ONLINE_SOLVERS = {"rolling-greedy", "rolling-hungarian", "rolling-cpsat", "rolling-routing"}`。
  `SOLVERS`(静的)は変えない。CLI の `--solver` と契約テストは、両方の和集合を対象にする。
- ログの `solver` 行: `name` = `rolling-<基底>`、`config` = 基底のソルバの `config` に `"base": "<基底>"` を足したもの
  (整数・文字列のみ。ADR-0004)。
- 静的なシナリオ(全タスクの到着が 0)では、エポックが1つで、基底のソルバと同じ結果になる(テストで確認する)。

### 4. ベンチマーク

- 静的なプリセット(`small`・`medium`・`large`)は変えない。対象は `SOLVERS` のまま。
- **動的なプリセットを足す。** `SOLVERS` と `ONLINE_SOLVERS` の両方を回し、表では
  **「静的(未来を知った順序、到着は無視)」と「ローリング(オンライン)」を区別**して並べる(ADR-0011)。
  - `dynamic-small`: 4台・10タスク、到着の窓 20(静的な makespan(約 25)の約 8 割)。
  - `dynamic-tiny`: AMR 1 + マニピュレーター 2・5タスク、窓 20。**オフライン最適を全探索で出す**(下記)。
  - 窓の既定は 20。W=10 ではローリングが静的に劣ることがあり、W=40 ではソルバ間の差が潰れる(予備測定)。
    窓を変えたいときは `--window N` で上書きできる(結果に窓を併記する)。
- **下界とオフライン最適:**
  - 一般のプリセットの下界は、これまでどおり `max(LB_task, 静的な CP-SAT の下界)`。
    動的な最適は静的な最適以上なので、これも**有効な下界**(ADR-0011)。ただし**弱い**
    (`dynamic-small` で約 22 に対し、達成値は 36 前後)ので、表では「参考値」と明記する。
  - **`dynamic-tiny` では、オフライン最適を全探索で出して基準にする**(全ての割当 × 実行順を `simulate` で評価)。
    この基準との比(競争比)を表に載せる。全探索は計算量の上限(割当 × 順序の数)を超えたら例外にする。
- 集計の指標は4つのまま(完了時間、総移動距離、稼働率、下界ギャップ)。比(オフライン最適に対する)は、
  `dynamic-tiny` の下界ギャップそのものになる(下界 = 最適)。

### 5. 到着時刻つきの CP-SAT(旧 ADR-0013)は作らない

- 予備測定のとおり、**小さな規模なら全探索で厳密なオフライン最適が得られ**、ローリングは最適の 1.05〜1.1 倍と
  分かる。大きな規模(4台・10タスク以上)での厳密な基準は、実装が重い(ロボットごとの時刻変数、
  ADR-0007 の定式化の拡張)わりに、この学習の目的に対して得るものが小さい。
- 大きな規模の動的な結果は、「静的との差」「ソルバ間の差」「参考値の下界」で示し、
  **最適からの距離は言わない**(README に明記する)。
- 見直しの条件: 大きな規模でオフライン最適からの距離を言う必要が出たとき。

### 6. 実装の分け方

| 順 | 内容 |
|---|---|
| 1 | `ready_at`(モデル、シミュレータ、ログ・スキーマ、ビューアの読み取り、下界)と4ソルバの対応 |
| 2 | `RollingSolver`、`ONLINE_SOLVERS`、CLI、契約テスト |
| 3 | 動的ベンチマーク(プリセット、全探索のオフライン最適、表の区別)、README に結果 |
| 4 | ビューア: 到着前のタスクの表示(必要ならADR) |

## Consequences

- (+) 静的なシナリオの結果・ログは変わらない(`ready_at`・`release_time` が 0)。
- (+) 既存の4ソルバを、基底としてそのままローリングに使える。契約テスト・CLI・ベンチマークに載る。
- (+) 「到着を考慮する価値」と「ソルバの最適性が情報の入り方に埋もれる」ことが、数字で見える。
- (+) 小さな規模では、オフライン最適との競争比を厳密に言える。
- (−) **4つのソルバすべてに手を入れる**(`ready_at`)。モデルとシミュレータの一致で守るが、改修の範囲は広い。
- (−) **ローリングの総移動距離は増える**(強いソルバ(Routing・CP-SAT)で約 +21〜29%)。完了時間だけを見ると見落とす。
- (−) **窓が短い(W=10)と、未来を知る静的が有利で、ローリングが劣る。** 比較の「静的」はオンラインの基準ではない
  (ADR-0011)。窓を併記し、「静的」の行は注記つきで表示する。
- (−) **窓が長いとソルバ間の差が潰れる**(W=40 で約 1.6%)。ソルバの優劣を言うには、窓が短めの条件が要る。
- (−) 解き直しを到着時刻のたびだけにしており、ロボットが空いたときには解き直さない。
  最適ではない確定の規則で、別の規則(下記)なら結果が変わりうる。
- (−) 解き直しの目的は、未確定のタスクの makespan で、確定済みの仕事の完了時刻を含まない。
  確定済みの完了時刻が全体を律速するときは、どの割当も同じ makespan になり、第2目的(移動)で決まる。
- (−) 大きな規模では、オフライン最適からの距離を言えない。小さな規模の結果を、一般化しない。
- (−) 1つの生成器・設定の予備測定。窓、台数、タスク数を変えると傾向が変わりうる。

## Alternatives considered

- **確定したタスクを変えず、新しいタスクだけを追加で割り当てる(待ち行列を解き直さない):**
  実装は単純だが、既に割り当てたタスクの再最適化ができない。試作の簡易ローリング(ADR-0011 の予備測定)は
  この方式で、再最適化つきと近い値だったが、ソルバの違いが見えにくい。解き直す方式にした。
- **ロボットが空いたときにも解き直す:** 情報は増えないので結果は変わらないことが多く、解く回数が増える。
  到着時刻だけにする。
- **`T` ちょうどに出発するタスクも確定する(`≤`):** `T` の時点の情報を使えなくなる。`<` にする。
- **移動の途中で行き先を変える(プリエンプション):** 現実的だが、実行の意味(ADR-0003・0011)の拡張が大きい。
- **`ready_at` を使わず、ダミーのタスクで表す:** ソルバが順序を守る保証がなく、スキルの細工も要る。
- **ソルバ自身に `release_time` を理解させる(オフラインの動的最適化):** 全ソルバの改修が大きく、
  CP-SAT は時刻変数が要る。オンラインの手法を並べる目的に合わない。
- **到着つきの CP-SAT で、大きな規模のオフライン最適を出す(旧 ADR-0013):** 上記のとおり見送る。
- **駆動役を `Solver` ではなく、別の層(シミュレータ側)に置く:** 純関数ではなくなり、契約テスト・CLI・
  ベンチマークに別の経路が要る。`Solver` のクラスにすれば、すべてがそのまま使える。
- **`SOLVERS` に `rolling-*` を足す:** 静的なプリセットで、基底と同じ結果の行が増えて紛らわしい。
  別のレジストリ(`ONLINE_SOLVERS`)にする。

## 見直しの条件

- 窓や規模を変えると、ローリングが静的に劣る、または差が出ない領域が広く、比較が成り立たない。
- 大きな規模で、オフライン最適からの距離を言う必要が出た(到着つき CP-SAT を検討する)。
- ロボットが空いたときの解き直しや、プリエンプションを入れたくなった。
- OR-Tools の更新で、`ready_at` を入れた CP-SAT・Routing の挙動が変わった。
