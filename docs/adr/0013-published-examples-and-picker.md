# ADR-0013: 公開する例の拡張と、比較の組を選べるビューア

- Status: Accepted
- Date: 2026-11-11

## Context

- 公開サイト(GitHub Pages)は、**貪欲法とハンガリアン法**の比較の例しか持たない。CP-SAT・Routing・ローリングホライズン、
  動的なシナリオ(Phase 3・4 の成果)は、手元でログを生成して `?log=` で開く必要があり、成果物(スマホで見られる
  比較ビューア。README)から見えない。
- ADR-0006 は、公開する例を「1つの例に2つのログ」に固定し、ADR-0007 は CP-SAT を公開物から外した
  (最適解が複数あるとき、選ばれる Plan が OR-Tools の版・OS で変わりうるため)。
  ADR-0006 の見直しの条件に、「3つ以上のソルバを並べたくなる」「公開するログが増え、`publish` の一覧が管理しにくくなる」
  とある。**その条件に当たった。**
- ユーザーの要望: 比較の組を柔軟にし(マニフェストで2つ選べる)、できるだけ色々なものを見られるようにしたい。
- 比較そのものは2画面のまま(ADR-0006)。3つ以上を同時に並べる設計は、スマホで読めなくなるので採らない。

## 予備測定(実現可能性)

候補の例(静的 4 + 動的 2)の全ソルバのログを、`render_log` で生成して測った。

| 例 | ログ数 | 生成時間 | サイズ |
|---|---|---|---|
| greedy-trap(静的) | 4 | 0.0 秒 | 4.5 KB |
| skill-trap(静的) | 4 | 0.0 秒 | 4.6 KB |
| seed1・4台・10タスク(静的) | 4 | 0.1 秒 | 15.0 KB |
| seed1・4台・15タスク(静的) | 4 | 0.4 秒 | 20.3 KB |
| seed1・4台・10タスク・窓 20(動的) | 8 | 0.4 秒 | 31.5 KB |
| seed0・3台・5タスク・窓 20(動的) | 8 | 0.4 秒 | 18.4 KB |
| **合計** | 32 | **1.4 秒** | **94 KB** |

- **ビルド時間・サイトのサイズは問題にならない。** Pages のビルドに、数秒しか足さない。
- **公開ログの再現性:** 同じプロセスで2回生成した CP-SAT・Routing・ローリングのログは、バイト一致した。
  公開ログは**ビルドのたびに、同じ OS・同じ OR-Tools の版で再生成する**ので、版・OS の揺れ(ADR-0007)は
  公開物の内容を壊さない(ビルドごとに最適解の選ばれ方が変わりうるだけで、makespan と総移動距離の値は変わらない)。
- **見せる価値のある例が、数字で選べる**(下の「例の選び方」)。

## Decision

### 1. 公開するソルバ

- 静的な4つ(`greedy`・`hungarian`・`routing`・`cpsat`)を、**全ての例**で公開する。
- ローリング版(`rolling-*`、4つ)は、**動的な例だけ**で公開する。静的な例では基底と同じ結果になる(ADR-0012)。
- `PUBLISHED_SOLVERS`(貪欲法・ハンガリアン法の固定)は廃止し、**例ごとに公開するソルバを持つ**
  (静的な例 = 静的な4つ、動的な例 = 静的な4つ + ローリング4つ)。`SOLVERS` と `ONLINE_SOLVERS` に追従する
  (ソルバを登録すれば、公開物に出る。静的なものは全ての例に、ローリングは動的な例に)。
- **ADR-0007 の「CP-SAT は公開しない」を改める。** 理由: 公開ログは毎回生成するので、
  Plan のバイト一致を前提にしない。テストは構造・シナリオの一致・指標の値を見る(golden のバイト一致は求めない)。
  CP-SAT の公開ログ・golden は引き続き**バイト一致を保証しない**(版・OS で Plan が変わりうる)。

### 2. 公開する例

静的な例(全て、静的な4つ):

| id | シナリオ | ねらい |
|---|---|---|
| `greedy-trap` | 手作り | 貪欲法が先に取って損をする(既存) |
| `skill-trap` | 手作り | スキルの罠(既存) |
| `seed1` | 生成(4台・10タスク) | 既定の規模(既存のデモと同じシード) |
| `static-spread` | 生成(4台・10タスク、シード 11) | ソルバの差が最も大きい(貪欲 47、ハンガリアン 25、Routing・CP-SAT 20) |
| `static-15tasks` | 生成(4台・15タスク、シード 1) | 規模を上げた例(貪欲 61、ハンガリアン 57、Routing・CP-SAT 40) |

動的な例(静的な4つ + ローリング4つ。窓 20。到着の窓は ADR-0011・0012):

| id | シナリオ | ねらい |
|---|---|---|
| `dynamic-rolling-wins` | 生成(4台・10タスク、シード 11) | ローリングが静的に大きく勝つ(貪欲 65 → ローリング貪欲 30。**静的な CP-SAT の 38 を、ローリング CP-SAT の 25 が大きく下回る**: 到着を無視した「最適」は、動的では最適ではない) |
| `dynamic-rolling-loses` | 生成(4台・10タスク、シード 3) | ローリングが静的に負ける(貪欲 41 → ローリング貪欲 46、CP-SAT 41 → ローリング CP-SAT 46。基底によらず負ける)。この到着の並びでは、未来を知る静的が有利 |
| `dynamic-tiny` | 生成(AMR 1 + マニピュレーター 2・5タスク、シード 0) | タスクが5つと少なく、経路を目で追える動的な例(貪欲 40 → ローリング貪欲 33、CP-SAT 32) |

- シードは**予備測定で選んだ**(ベンチマークの代表ではなく、**見せるための例**。README と画面に注記する)。
  「ローリングが勝つ例」だけを並べると誤読を招くので、**負ける例**も入れる。
- 例は `mrta.publish` の定数として持つ。増やすときは、そこに足す。
- 従来の `demo.jsonl`(シード 1、貪欲法)は残す(ビューアの既定の読み込み先)。

### 3. マニフェスト v2

```json
{"examples":[{"id":"greedy-trap","title":"…","logs":[{"file":"greedy-trap-greedy.jsonl","solver":"greedy"},{"file":"greedy-trap-cpsat.jsonl","solver":"cpsat"}],"dynamic":false}],"manifest_version":2}
```

- `logs` は**2本以上**の、`{file, solver}` の配列。`solver` は表示用の名前で、ログの `solver.name` と一致する
  (ビューアはログを読まずに選択肢を出せる)。`file` は `manifest.json` と同じディレクトリからの相対パス。
- 例に `dynamic`(真偽値)を持たせる。表示の注記(到着前の凡例の予告、「静的は未来を知っている」)に使う。
- **版を 2 に上げる。** v1 は `logs` が2本の文字列で、N本・オブジェクトに広げる変更は互換でない。
  ビューアは v1 と v2 の**両方を読む**(v1 は2本の組として扱う)。未対応の版は、これまでどおりリンクを出さない
  (ADR-0006)。古いビューアは v2 を読めずリンクを出さないが、閲覧は妨げない。
- 決定的に書く(ログと同じ規則)。ログの並びは、**静的 → ローリングの順**、各群は名前順。

### 4. ビューア: 比較の組を選ぶ

- 「比較の例」を、**例ごとの選択**にする。各例に、A と B の2つの選択(`<select>`)と「比較する」のリンクを置く。
  選択肢は、その例の `logs`(ソルバ名)。
- 既定の組: 先頭2本ではなく、**例ごとに意味のある組**を `default`(マニフェストの `a`・`b`)で指定する。
  (静的な例は貪欲法 vs CP-SAT、動的な例は静的な貪欲法 vs ローリング貪欲法など。）無ければ先頭の2本。
- A と B が同じログのときは、リンクを出さず、理由を示す(同じものの比較は無意味)。
- リンクは従来どおり `?log=…&log=…`(URL で共有できる)。選択は JS で `href` を更新するだけで、サーバーは要らない。
- 選択の UI も、盤面にテキストを描かない方針(ADR-0006)の外(HTML)に置く。
- 1つの例の中に、**静的ソルバとローリングが混在**する動的な例では、選択肢の名前に種別を添える
  (「greedy(静的・到着を無視)」「rolling-greedy(ローリング)」)。静的は未来を知っている(ADR-0011)。

### 5. 公開物のテスト

- `mrta publish` の出力: 全ログの構造(`check_log_structure`)、**同じ例のログの `scenario` 行が一致**、
  マニフェストの参照するファイルが全て存在し、`solver` がログの `solver.name` と一致する。
- **公開ログのバイト一致は検査しない**(CP-SAT の Plan は版・OS で変わりうる。ADR-0007)。
  代わりに、makespan と総移動距離を、シミュレータで評価し直した値と照合する。
- ビューア: マニフェスト v1・v2 の読み取り(版・N本・不正な `file`・`solver` の欠落)、選択の組から作る URL、
  同じログの選択。E2E: 例の選択で比較画面が開く、A・B を変えるとリンクが変わる、静的と動的の例が両方出る。
- 既存の2本組(v1)のマニフェストを読めること(後方互換)。

## Consequences

- (+) 公開サイトで、CP-SAT・Routing・ローリング・動的な到着の結果を、スマホから比較できる。
  成果物の価値が、Phase 3・4 の成果まで届く。
- (+) 「ローリングが勝つ例」と「負ける例」の両方を見せるので、誤読(いつも勝つ)を避けられる。
- (+) ビルドの負担が小さい(1.4 秒、94 KB)。
- (+) 例を `mrta.publish` の定数に足すだけで増やせる。
- (−) **公開する例の選び方に、作り手の恣意が入る。** 予備測定で選んだ「見せるための例」で、代表ではない。
  README と画面に注記する(ADR-0005 の手作りシナリオと同じ扱い)。結論は統計(ベンチマーク)で出す。
- (−) **CP-SAT の公開ログの Plan は、ビルドごとに変わりうる**(版・OS の揺れ)。値(makespan・総移動距離)は同じ。
  ブックマークした比較の見た目(ロボットの経路)が、ビルド後に変わる可能性がある。
- (−) マニフェストが v2 になり、古いビューア(キャッシュされた古いサイトなど)は v2 を読めずリンクを出さない
  (閲覧は妨げない)。
- (−) 選択肢が増えると、スマホの画面で操作が増える。選択は例ごとに2つで、既定の組から1タップで開けるようにする。
- (−) ビューアに選択の UI が加わり、テストと保守の対象が増える。

## Alternatives considered

- **例の組を固定して、組ごとに別の例にする(案 A):** 小さいが、4ソルバの全ペア(6通り)× 例の数で
  リンクが爆発する。選択のほうが小さい。
- **全ソルバを並べる表(2画面を超える比較):** ADR-0006 の見直しの条件に当たるが、スマホで読みにくい。
  2画面の比較に、選択を足すほうが、既存の設計に沿う。
- **ログごとに種別をマニフェストに持たせず、ファイル名から導く:** 小さいが、命名規則への暗黙の依存になる。
  `solver` を明示する。
- **マニフェストを v1 のまま拡張する:** `logs` を2本に限る検証を外すだけで済むが、古いビューアが
  N本の例を黙って捨てる。版を上げて、壊れ方を明示する。
- **ベンチマークの結果(統計)を公開サイトに載せる:** ADR-0008 で見送った。到着の窓・規模ごとの統計の表示は、
  別の設計になる。
- **CP-SAT は引き続き公開しない:** 再現性の懸念を避けられるが、最適解という物差しが見えない。
  公開ログはビルドごとに生成するので、懸念は小さい。

## 見直しの条件

- 例が増え、`mrta.publish` の定数の管理や、選択の UI が煩雑になる。
- ビルドごとに CP-SAT の公開ログの経路が変わることが、読み手の混乱を招く(Plan のバイト一致を保証する、
  またはCP-SAT のログに版を併記する)。
- 3つ以上を同時に並べたくなる(別の表示を設計する)。
- スマホで、選択の操作が負担になる。
